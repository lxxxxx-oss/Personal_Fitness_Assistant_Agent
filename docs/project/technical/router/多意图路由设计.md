# 多意图路由设计

本文只说明当前已经落地的受控多意图路由。单意图评分、评测数字和 LLM/embedding A/B 结论见[路由优化状态](./路由优化状态.md)。

## 1. 解决的问题

单一 `intent` 无法完整表达“先分析动作，再查纠正方法”这类请求。当前 Router 因此同时记录主意图、次意图和执行顺序。可靠多意图一旦成立，五条已注册子图可以按用户表达自由组合；系统不再维护固定组合白名单，但仍用合法意图、去重和最多三步约束执行范围。

代码层保留五条执行路径：

```text
chat | search | diet | motion | mcp
```

其中 `diet` 负责营养和饮食规划，`mcp` 负责外部菜谱工具调用；产品层可以把二者合并介绍为“饮食与菜谱”。

## 2. 当前状态字段

Router 在内部 `RouterState` 中记录：

```python
_primary_intent: str
_secondary_intents: list[str]
_route_plan: list[str]
_multi_intent_reason: str
_needs_clarification: bool
```

- `_primary_intent`：本轮优先任务，公开响应中的 `intent` 与它一致。
- `_secondary_intents`：同一句话中识别出的次要任务。
- `_route_plan`：通过校验后实际执行的子图顺序。
- `_multi_intent_reason`：供日志、调试和评测解释。
- `_needs_clarification`：两个候选接近、但缺少可靠复合任务结构时暂停执行并请求澄清。

这些是内部执行字段，不属于当前公开 API 响应协议。

## 3. 识别策略

主意图与执行顺序由确定性策略决定：

- “先/再/然后”等显式顺序词优先遵守用户顺序。
- “顺便/同时/并且/另外”等并列词只有在两个分句都能可靠识别时才形成多意图；单独出现弱连接词不会强行扩展任务。
- 上传动作数据、`.npz` 或姿势判断优先 `motion`。
- “最新、最近、研究、权威说法”优先 `search`。
- 具体菜名、食材和做法进入 `mcp`；摄入量和饮食规划进入 `diet`。
- “不需要具体做法”等否定约束会抑制 `mcp`。
- 信息不足且没有形成两个有效候选时退回 `chat`；两个候选都过最低分但无法安全决策时进入澄清，不凭空扩展任务。

多意图识别不额外调用模型；本地 Qwen classifier 和 embedding fallback 都是默认关闭的实验能力。

## 4. 歧义澄清与跨轮恢复

“两个分数接近”不等于“用户同时提出两个任务”。系统先检查句子中是否存在可靠的复合任务证据：例如“先……再……”的顺序关系，或两个能独立识别的并列分句。有这些证据时才生成多意图计划；只有两个候选能力都过最低分、分值接近，但原句又无法确认用户是选其一还是两者都要时，才进入澄清。

当前链路为：

```text
两个候选接近且无法确定
  -> 用确定性模板点名两个候选及其差异
  -> 本轮只返回澄清问题，不调用业务子图或额外 LLM
  -> 将原始问题、候选项、问题和分数写入 task_states
  -> 下一轮识别“1/前者”“2/后者”、能力名称或“两个都要”
  -> 将原始问题与用户选择合并，恢复单路或多路执行
```

若回答仍不明确，系统会重复候选问题；用户说“算了/不用了/取消”或直接提出一个可可靠识别的新任务时，会清除待澄清状态。持久化按 `user_id + conversation_id` 隔离，正常会话可跨后端重启恢复；临时会话只保存在当前进程内。该状态属于短期任务控制状态，不是长期用户记忆。

## 5. 受控执行

简单请求仍只执行一个子图。可靠多意图计划不再检查固定组合白名单，而是统一经过三项校验：

1. 每个意图必须属于已注册的 `chat/search/diet/motion/mcp`。
2. 同一意图在一个计划中只执行一次。
3. 单次请求最多执行三步，超出部分截断并写入 warning。

例如 `diet -> mcp`、`mcp -> search`、`motion -> chat` 都属于可执行的合法组合，先后顺序取自用户原句，不按预设组合重排。

执行过程为：

```text
route_plan
  -> 合法性、去重、最多三步校验
  -> 按用户表达顺序逐个执行子图
  -> 单独记录每步结果或错误
  -> final synthesis 统一生成最终回答
```

单步计划不增加合成调用；多步计划只在末尾生成一次。每一步的结果或异常独立写入状态，某一步失败时继续执行后续步骤、保留其他成功结果，并在最终回答和 `warnings` 中说明部分失败；只有全部步骤失败时才返回整体错误。

## 6. 评测与边界

`data/eval/router_challenge_eval.jsonl` 同时标注 `primary_intent`、`secondary_intents` 和 `route_plan`，用于检查识别和规划，不只检查公开 `intent`。当前基线统一见[项目证据](../../项目证据.md)，避免在设计文档复制易过期数字。

当前没有证明生产流量上的泛化能力。这里的“开放组合”也不等于开放式 Planner：Router 只能从五个已注册意图中生成至多三步的顺序计划，不会动态发明工具、创建循环、推断跨步骤数据依赖或并行执行。当前澄清答案采用确定性别名和序号解析，能够稳定处理常见回答，但不宣称理解任意自由表达；无法解析时会再次澄清，而不是猜测执行。

## 7. 面试回答

> 我先区分“明确复合任务”和“候选意图竞争”：有可靠顺序或并列结构时生成受控 route plan；只有两个候选都成立但无法判断用户取舍时，才返回点名差异的澄清问题，并把原问题和候选状态按会话持久化。用户回复序号、能力名称或“两项都要”后，系统恢复对应单路或多路执行。这样既不会把歧义误当成多意图，也不会在不确定时擅自调用工具。
