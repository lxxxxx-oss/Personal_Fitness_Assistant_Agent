# 上下文渐进式压缩设计

> **定位说明**：本文档最初用于设计上下文压缩管道，现在同时保留“实施前基线、目标设计和当前落地状态”。第一节中的旧机制明确标记为历史基线，不能当作当前代码事实。
>
> 上下文压缩 ≠ 记忆系统。记忆系统决定存什么、存多久、怎么存；上下文压缩决定进 prompt 时带什么、怎么压缩、怎么拼接。

## 1. 实施前基线与当前状态

### 1.1 实施前记忆机制（历史）

| 组件 | 实施前行为（仅用于历史对比） |
|---|---|
| 存储 | `SlidingWindowMemory`，基于 `collections.deque`，`max_turns=6`（12 条消息），FIFO 淘汰 |
| 会话隔离 | 实施前只有 `_sessions: Dict[str, SlidingWindowMemory]` 进程内缓存，重启会丢失；当前已增加 SQLite 恢复 |
| 消费方 | 实施前仅 Chat 子图读取 `memory[-6:]`；当前主要文本 Prompt 已由 PromptBuilder 统一组织 |
| 压缩 | **无**。超过 6 轮直接丢弃，没有摘要、提炼或嵌入化 |

### 1.2 实施前各子工作流使用情况（历史）

| 子图 | 读 memory | 写 memory | 说明 |
|---|---|---|---|
| Chat | ✅ `memory[-6:]` | ❌ 不写，只靠 `main.py` 的 `add_turn()` | 注入 Prompt "对话历史" 段落 |
| Diet | ❌ | ❌ | 不上传上下文，上一轮说"素食者"下一轮不知道 |
| Search | ❌ | ❌ | 无跨轮上下文 |
| Motion | ❌ | ❌ | 无跨轮上下文 |
| MCP | ❌ | ❌ | 无跨轮上下文 |

### 1.3 实施前硬约束（历史）

- `MAX_PROMPT_CHARS = 8192`（`app/config.py`），由 PromptBuilder 和 LLMLoader 共用，超出直接拒绝
- 单进程模型生成全局串行锁 `_MODEL_GENERATION_LOCK`
- 记忆条目仅 `{role, content}`，无时间戳或元数据

### 1.4 当前状态与边界

当前代码已经完成最小上下文工程闭环，但还没有实现本文设计中的全部生产化能力。

| 层级 | 当前状态 |
|---|---|
| 已实现 | `PromptBuilder` 统一主要文本 Prompt；从本地模型配置解析上下文窗口并动态计算输入预算；字符或估算 token 任一超阈值即触发本轮 compact；角色/安全规则、当前问题及已确认的伤病、过敏、禁忌等安全记忆固定保留；核心上下文按队列轮询装入完整条目，普通信息和软记忆最后填充，超预算条目整条跳过；本地模型在真正推理前再用 tokenizer 精确校验，远程模型先执行项目字符硬上限检查并由服务端校验其模型边界；会话可从 SQLite 恢复；持久化摘要支持事务写入、active 替换、消息边界、确定性 signals/evidence、最近六轮保留、三种聊天协议接入和最终回答 Prompt 注入 |
| 部分实现 | 工具结果和长期记忆受总字符/token 预算约束，但还没有为每个区段配置独立配额；前端只展示部分执行信息 |
| 生产化补齐 | 各 Prompt 区段的独立 token 配额、模型摘要、完整前端状态卡片、更大规模摘要质量评测、跨实例上下文和审计治理 |

面试时应表达为：

> 当前版本完成了“近期对话 + 结构化状态 + 长期记忆 + 确定性 compact + 模型派生预算 + Prompt 元数据”的最小闭环。会话摘要以 JSON 保存 signals 和可追溯 evidence；构建阶段先固定保留安全规则、当前问题及伤病/过敏/禁忌等确认后的安全记忆，再把检索证据、长期记忆、结构化摘要、近期对话和会话摘要作为核心候选队列，按优先级每轮各尝试一条。单条放不下时跳过并继续其他队列，一轮没有任何成功项时停止，剩余空间最后再给普通信息和待验证软记忆。这样既保留优先级，又避免某一类内容一次性吃满预算。本地模型推理前再用实际 tokenizer 做硬校验；DeepSeek 等远程模型使用项目字符硬上限预检，最终模型窗口由服务端校验。摘要不调用 LLM，因此可复现但语义归纳有限；模型摘要、语义化安全标签和跨实例治理仍是生产化方向。

## 2. 原始目标设计与当前完成度

下面五项是设计目标，不是都已完成：第 1—3 项已有最小实现；第 4 项只有后端 execution 元数据，没有前端可展开气泡；第 5 项当前由各 Prompt 模板内嵌安全规则实现，没有独立 `data/rules/safety_rules.md` Pin 文件。

1. **渐进式压缩**：保留最近 6 轮原文，6 轮之外的历史 → 结构化提取后丢弃原文
2. **全局覆盖**：所有子图（Chat/Diet/Search/Motion/MCP）统一受益于压缩后的状态
3. **代码规则为主**：子图执行时由代码直接写入结构化字段，LLM 只做兜底提取
4. **可观测**：压缩发生时在对话流中插入系统消息气泡，用户可点击展开查看状态
5. **安全约束永不被截断**：规则写入磁盘 + 代码固定注入 Prompt 最前端

## 3. 触发机制

### 3.1 混合触发策略

当前代码里有两类触发：

| 触发点 | 配置 | 当前行为 |
|---|---|---|
| 持久化会话摘要 | `CONVERSATION_SUMMARY_TRIGGER_CHARS=3000` 或 `CONVERSATION_SUMMARY_TRIGGER_TOKENS=900` | 回答保存后，较早且未压缩消息命中任一阈值时生成结构化证据摘要；最近 6 轮（12 条消息）不进入摘要 |
| 本轮 Prompt compact | 默认在可用输入预算的 80% 触发 | 固定保留角色/安全规则、当前问题和已确认安全记忆；核心候选队列按优先级逐轮各尝试一条，单条放不下则跳过并继续其他队列，一轮无新增时停止，剩余空间再填普通信息与软记忆；本地模型由推理前 tokenizer 精确兜底，远程模型由字符硬上限预检和服务端模型窗口共同兜底 |

“最近 6 轮原文 + 更早轮次结构化证据摘要”已经统一落地。Prompt 最终只保留并注入 `MEMORY_MAX_TURNS * 2` 条近期消息，摘要器使用同一配置保护边界；但服务重启恢复当前仍会先从 SQLite 读取完整会话，再由滑动窗口淘汰旧消息。按摘要边界和最近窗口进行数据库级有限查询已记录为未来优化，尚未实施。摘要仅整理原始片段和信号索引，不调用额外 LLM。

```
最近 6 轮原文始终保留
  +
总 context 超过 token 阈值时触发压缩
  →
6 轮以外的历史 → 结构化提取后丢弃原文
```

### 3.2 模型上限与动态预算

模型声明的上下文窗口是硬上限，不等于应用可以全部拿来放 Prompt。启动时按以下顺序读取当前本地模型的真实声明：`config.json`（优先 `text_config`）中的 `max_position_embeddings`、`n_positions`、`max_sequence_length`、`seq_length`、`model_max_length`，找不到时再检查 `tokenizer_config.json`。Tokenizer 常见的超大哨兵值会被忽略，避免误判为真实容量。

设模型硬上限为 `C`、最大生成预留为 `G`、模板和估算误差安全余量为 `S`，则：

```text
最大输入预算 P = C - G - S
压缩触发阈值 T = floor(P × r)
```

默认 `G=1024`、`S=256`、`r=0.8`。例如模型文件声明 `C=8192` 时，`P=6912`，`T=5529`。这只是公式示例；对外报告当前模型数值时必须同时给出 `model_context_window_source`，不能把缺少模型文件时的回退值说成真实上限。

| 参数 | 默认 | 说明 |
|---|---:|---|
| `MODEL_CONTEXT_WINDOW` | `0` | 可选人工上限；模型已有声明时只能向下收紧，不能扩张模型硬上限 |
| `MODEL_CONTEXT_FALLBACK_TOKENS` | `4096` | 本地模型元数据不可用时的安全回退，不属于实测/真实上限 |
| `MODEL_MAX_TOKENS` | `1024` | 为本次生成预留的最大 token 数 |
| `CONTEXT_SAFETY_TOKENS` | `256` | 为聊天模板、估算误差和边界留出的安全余量 |
| `CONTEXT_COMPACT_TRIGGER_RATIO` | `0.8` | 在最大输入预算的 80% 处主动压缩 |
| `MAX_PROMPT_TOKENS` / `COMPACT_TRIGGER_TOKENS` | `0` | `0` 表示按上述公式自动计算；显式值只作为更严格的应用上限 |
| `MAX_PROMPT_CHARS` / `COMPACT_TRIGGER_CHARS` | `0` | `0` 时按 token 预算的 4 倍派生，作为预构建字符保护线 |
| `CONVERSATION_SUMMARY_TRIGGER_TOKENS` / `MAX_TOKENS` | `900 / 360` | 较早消息的持久化摘要阈值，和模型 Prompt 硬上限是两个概念 |

`PromptBuilder` 构建时尚未调用 tokenizer，因此用保守估算提前触发 compact。本地模型路径中，`LLMLoader` 套用 chat template 并 tokenize 后，会精确检查应用输入预算以及 `input_tokens + max_new_tokens <= C`；DeepSeek 等远程 API 路径没有本地同款 tokenizer，只能先检查项目字符硬上限，最终模型窗口由 provider 校验。因此，项目不能把远程模型的估算 token 数包装成精确计数。

触发检查点：本轮 Prompt compact 发生在 `PromptBuilder.attach()`；持久化会话摘要发生在 `_persist_conversation_turn()` 保存完整 turn 之后。两者目的不同：前者保护本轮 prompt 长度，后者保护跨请求会话连续性。

### 4.1 字段定义

当前 `RouterState._structured_state` 的实际字段以 `app/graph/structured_state.py` 为准：

| 字段 | 类型 | 写入方式 | 写入方 | 说明 |
|---|---|---|---|---|
| `task` | `Dict` | 代码规则 | Router 节点 | 当前 primary intent、route plan 和输入摘要 |
| `decisions` | `List[Dict]` | 代码规则 | Router 节点 | Router 决策（source / intent / confidence） |
| `profile` | `Dict` | 代码规则 | Diet 子图 | 用户画像（身高/体重/性别/目标/偏好），覆盖式更新 |
| `knowledge_sources` | `List[str]` | 代码规则 | Chat/Diet 子图 | 已引用过的 RAG 知识来源标识，去重 |

`files`、`errors`、`todos` 以及基于 LLM 的 `user_context` 提取属于原始目标设计，当前没有进入实际默认结构。

### 4.2 目标字段上限（尚未完整实现）

下表是防自膨胀目标。当前只有工具 preview 单条 800 字符和 PromptBuilder 总字符/估算 token 预算等局部限制，没有对每个结构化列表完整执行下表裁剪。

| `decisions` | 保留最近 **5 条** |

### 4.3 user_context 的目标价值

结构化字段主要捕获**系统行为**（错误/决策/文件），但用户可能在对话中透露关键信息：
- "我膝盖有点疼"
- "我是素食者"
- "最近在备考没时间去健身房"

这些不是错误、不是文件、不是决策、不是 TODO。目标方案计划用固定模板保存这类事实，但当前 `user_context` 只是空的预留字段；真正长期保存仍只走显式“记住”和敏感候选确认。

## 6. 压缩执行流程

当前实际流程：

```text
请求进入
  -> 按 user_id + conversation_id 恢复 SlidingWindowMemory
  -> 读取 active compact summary
  -> 只保留未被 summary 覆盖的近期消息作为 memory
  -> PromptBuilder 注入长期记忆、active summary、近期原文和当前问题
  -> 如果本轮 prompt 超过模型派生的字符保护线或估算 token 触发线，执行 priority_round_robin_v3 裁剪
     -> 固定保留角色/规则、当前用户问题和确认后的安全记忆
     -> 将 RAG、工具结果、记忆、摘要和近期对话拆成不可再切的逻辑条目
     -> 各队列内部沿用上游相关性/新旧顺序；核心队列按优先级每轮各尝试一条
     -> 单条放不下时跳过并继续本轮其他队列；一轮零新增时停止核心装箱
     -> 剩余空间最后填充普通信息和待验证软记忆
     -> 对结果执行字符与估算 token 硬预算检查
  -> 本地模型：LLMLoader 套用 chat template 并 tokenize，精确校验应用输入预算和模型硬上限
     远程模型：先校验项目字符硬上限，再由 provider 校验实际模型窗口
  -> 回答完成后，用户/助手消息在 SQLite 中单事务写入
  -> 如果未压缩旧消息超过字符或估算 token 阈值，生成新的结构化证据 active summary 并推进 last_compacted_message_id
```

设计初稿中的 LLM 兜底提取仍是后续方向；当前摘要使用 `conversation_summary.build_extractive_summary()`，只截取和拼接原文片段，便于测试和面试解释。

下面是原始目标流程，不是当前代码逐项行为：

```text
每次子图 generate_node 构建 prompt 前：

1. 计算当前 prompt 总长度（系统规则 + 结构化状态 inject + memory + 工具 preview + 用户输入）
2. 如果字符数和估算 token 均未超过模型派生触发线 → 跳过，正常拼接
3. 如果任一超过触发线：
   a. 保留 memory[-12:]（最近 6 轮原文），其余丢弃
   b. 从丢弃的轮次中，代码规则已写入的字段不动
   c. LLM 兜底扫描丢弃的轮次，提取 todos + user_context，追加到结构化状态
   d. 各字段按 4.2 上限裁剪
   e. 重新拼接 prompt（系统规则 + inject + 6 轮原文 + 工具 preview）
   f. 在对话流生成一条系统消息气泡："📋 对话已浓缩，点击查看摘要"
   g. 气泡展开后展示结构化状态（除 tool_results_summary 完整内容外，显示字段摘要）
```

## 7. Prompt 拼接规范

### 7.1 目标统一顺序

当前主要文本 Prompt 已由 PromptBuilder 集中构造，但 Chat、Diet、Search、Motion、MCP 的具体区块仍按任务不同，并非都严格等于下面六段。下表是收敛方向，不应说成所有 Prompt 的不可变字节级顺序。

```text
[1] # 系统安全规则        ← 从 data/rules/ 加载，永不压缩
[2] # 硬约束（代码注入）    ← 每个子图都有，永不压缩
[3] # 对话摘要             ← 结构化状态注入（可展开）
[4] # 近期对话（最近 6 轮） ← 原文保留
[5] # 工具结果（preview）   ← 限流后的摘要
[6] # 用户问题             ← 本轮输入
```

### 7.2 安全规则的 Pin 机制

**目标磁盘文件**：`data/rules/safety_rules.md`（当前不存在）
- 包含医疗免责声明、使用边界、隐私提示
- 目标是在启动时加载并固定注入；当前安全规则直接写在各任务 Prompt 模板中

**代码注入**：[2] 位置由子图代码根据任务类型注入对应的硬约束：
- Chat: "只基于参考资料回答，不编造健身建议"
- Diet: "画像缺失时提示用户补充，禁止推荐极端饮食"
- Motion: "不替代专业教练做动作诊断"

本轮裁剪固定保留 [1][2][6]，并额外固定保留长期记忆中已确认的伤病、过敏、禁忌、不耐受和基础疾病等安全信息，不会截断当前用户问题。其余核心内容分为“检索/工具证据、已确认画像与长期记忆、结构化 compact summary、近期对话、会话摘要”五类候选队列；队列内部沿用上游相关性排序，近期对话按新到旧排序。装箱仍遵守上述优先级，但每轮每个核心队列最多尝试一条：某条放不下就整条跳过并继续其他队列，一整轮没有任何新增才停止。之后再用剩余空间装普通信息和待验证软记忆。RAG chunk、记忆条目、摘要条目和一轮用户/助手对话都以完整条目为最小单位，不按字符从中间截断。这里没有人为设置固定比例配额；轮询只提供最低限度的跨类别公平性，最终是否保留仍取决于条目大小和预算。

当前 `priority_round_robin_v3` 的确定性步骤是：

1. 固定装入系统规则、安全约束和当前问题。
2. 固定装入确认后的伤病、过敏、禁忌等安全记忆。
3. 建立候选队列，队列内部按上游相关性和时间顺序排列。
4. 核心队列按优先级每轮各尝试一条。
5. 放不下某条时跳过，继续尝试本轮其他队列。
6. 一轮没有任何内容成功加入时停止核心装箱。
7. 剩余空间再装普通信息和低信任软记忆。
8. 最后检查字符与估算 token 硬上限；本地模型推理前再用真实 tokenizer 精确复核。

## 8. 工具结果分层返回

本节是原始三段式目标设计。当前已经实现的是 `_structured_state.tool_results_summary` 中的短 preview，以及 ToolResult/执行元数据；没有 `_tool_result_cache`、full/index 查询接口或“点击展开完整工具结果”能力。

### 8.1 三段式结构

| 层级 | 内容 | 长度 | 何时展示 |
|---|---|---|---|
| **preview** | 工具名 + 状态 + 简短摘要 | 目标 < 500 字符；当前单条 summary 上限 800 字符 | 按任务 Prompt 需要注入 |
| **full** | 完整 ToolResult.data | 无限制 | 存入临时缓存，用户点击/追问时展开 |
| **index** | 调用 ID + 时间戳 | — | 用于查询 full 结果的 key |

### 8.2 目标临时缓存（未实现）

- 存储位置：`_tool_result_cache[user_id]`，和 `_sessions` 同生命周期
- Key：`{execution_id}` 或 `{component}_{timestamp}`
- 淘汰：每个用户最多保留 **20 条**，超出时 FIFO 淘汰

### 8.3 各工具 preview 格式

| 工具 | Preview 格式 |
|---|---|
| Tavily Search | `[搜索] "{query}" → {count} 条结果`（不展示 content 全文） |
| RAG Retrieve | `[知识检索] "{query}" → {count} chunks, 来源: {sources}` |
| MCP get_recipe | `[菜谱] {dish_name} — 配料: {ingredients[:3]}... — 步骤: {n}步` |
| Motion compare | `[动作对比] vs {reference}: DTW={dtw}, cosine={cosine}, shape={shape}` |

## 9. 摘要模板（LLM 兜底专用）

这是未启用的目标模板。当前压缩不调用 LLM 提取 TODO 或用户事实；active summary 使用确定性原文摘录，prompt compact 使用确定性的分队列轮询装箱与整条淘汰。

## 待办事项
- {事项1}
- {事项2}
（没有则写：未记录）

- {事实1}
- {事实2}
（没有则写：未记录）

**关键约束**：
- 只在压缩触发时调用，每次最多一次 LLM 推理
- 温度设 0.0（确定性输出）
- max_new_tokens = 256
- 输出不符合模板 → 丢弃，标记 warning，不影响主流程

## 12. 实现阶段

实现顺序遵循一个原则：先让上下文“可控可测”，再做自动摘要。不要一开始就引入复杂 LLM 压缩，否则很难判断问题来自记忆写入、prompt 组装还是摘要质量。

当前状态：阶段 1 已完成；阶段 2 完成实际最小字段但未实现目标字段上限；阶段 3 只完成 preview，没有 full/index 缓存；阶段 4 已实现确定性的核心队列轮询装箱、普通/软信息末尾填充和整条淘汰，没有 LLM TODO 提取；阶段 5 已完成后端裁剪诊断元数据，前端卡片未实现；阶段 6 完成 active summary 与长期记忆注入，但 compact 不会自动提升长期事实。

### 阶段 1：Prompt Builder 统一入口
- 把 Chat/Knowledge 的 prompt 拼接逻辑先收敛到统一 builder。
- 固定注入顺序：安全规则 → 硬约束 → 记忆/摘要 → 最近对话 → 工具 preview → 用户问题。
- 保留现有 `SlidingWindowMemory`，不急着改变底层存储。
- 验收标准：现有问答链路不回退，prompt 长度可观测。

### 阶段 2：结构化状态最小闭环
- 在 `RouterState` 中新增 `_structured_state` 字段。
- 实现字段上限裁剪逻辑。
- 先让 Router 写入 `task` / `decisions`，Search/MCP 写入 `tool_results_summary`。
- 验收标准：多意图链路中第二步能读取第一步的结构化状态。

### 阶段 3：工具结果 preview
- Search/MCP/RAG 先实现 preview 格式化。
- 完整结果进入临时缓存，prompt 中只放 preview。
- Motion 暂时只记录上传文件元信息，不急着把标准动作比较结果做复杂注入。
- 验收标准：长搜索结果不会直接撑爆 prompt。

### 阶段 4：压缩触发与兜底提取
- 从本地模型声明的上下文窗口派生字符/token 双触发线；本地推理前使用真实 tokenizer 做硬校验，远程 API 使用字符硬上限预检并由 provider 校验实际窗口。
- 超阈值时固定保留角色/安全规则、当前问题和确认后的安全记忆；核心上下文按语义边界拆分并分队列轮询，普通信息和软记忆最后填充，不能完整放入的条目整条淘汰。
- 若固定内容本身超过触发目标，不截断当前问题；若进一步超过项目字符硬预算会直接拒绝，本地模型还会用真实 tokenizer 校验，远程模型的最终窗口越界由 provider 返回明确错误，而不是静默生成残缺请求。
- LLM `todos` / `user_context` 兜底提取仍未启用。
- 验收标准：安全规则与当前问题保持完整，可选上下文不产生半条内容；正常情况下回落到触发阈值内，硬越界能被精确校验拦截。

### 阶段 5：可观测性与前端展示
- `_prompt_meta.compact_diagnostics` 和 API `execution` 记录 compact 策略、预算结果及淘汰数量。
- Web UI / 小程序显示“对话已浓缩”系统消息。
- 展开后展示结构化状态摘要。
- 验收标准：用户和开发者都能知道什么时候压缩、压缩保留了什么。

### 阶段 6：与持久化记忆联动
- 读取 memory-system 中的 active compact_summary 和长期 memory 注入。
- compact 中抽取出的长期事实必须交给 Memory Writer 判断，不直接写入长期记忆。
- 验收标准：上下文压缩和长期记忆边界清晰，不绕过隐私确认。

## 13. 风险与边界

下表多数是原始 LLM 压缩/缓存方案的目标风险控制，不代表当前已有 2 秒摘要 SLO、每用户 20 条缓存或前端调试入口。当前整条淘汰方案消除了“半条证据/半轮对话”和规则被尾部硬切的问题，轮询也降低了单一高优先级类别独占预算的概率；但优先级和安全关键词识别仍是启发式，一个很长但相关的可选条目仍可能整体放不下，低优先级内容也可能包含当前任务所需信息。此外，抽取式摘要仍可能冗余，PromptBuilder 的预估 token 与真实 tokenizer 仍存在误差，多实例也缺少并发治理。推理前的精确计数只负责阻止越界，不保证裁剪后的信息质量。

| 风险 | 处理 |
|---|---|
| 压缩触发 LLM 调用增加延迟 | 仅压缩时调用一次，温度 0.0，max_tokens=256，预计 <2s |
| 结构化状态字段语义漂移 | 代码规则写入的字段不由 LLM 控制，确保稳定性 |
| 多意图场景下状态被错误清除 | `collect_route_result_node` 显式保留 `_structured_state` |
| 临时缓存无限增长 | 每用户最多 20 条，FIFO 淘汰 |
| 压缩后信息不可逆 | 可在系统消息中提供 `user_id` 和压缩时间戳，便于调试 |
| 压缩摘要绕过隐私确认 | compact 只服务当前会话上下文；如果要提升为长期记忆，必须经过 Memory Writer 和敏感信息确认规则 |

## 14. 评测体系

上下文压缩的评测目标不是证明“摘要写得好不好看”，而是证明：长对话之后，关键事实仍然能进入 prompt，安全规则不会丢，prompt 长度不会爆。

当前已落地的是 14 条 Memory + Context + RAG 联动 benchmark，其中 6 条持久化摘要场景；另有 Prompt 裁剪专项回归覆盖正常回落到触发阈值、安全规则、当前问题与安全记忆完整保留、超长高优先级条目跳过后继续其他队列、RAG/记忆/对话条目整条保留或淘汰，以及固定内容自身超过目标时不静默截断。下面 20—30 条、LLM 摘要异常和前端状态展示属于扩大后的目标评测集。

### 14.1 评测样本类型

| Case 类型 | 测什么 | 示例 |
|---|---|---|
| 长对话关键事实保留 | 压缩后用户关键信息是否仍被注入 | 第 1 轮说“我是素食者”，第 10 轮问饮食建议 |
| 安全规则保留 | 压缩后安全规则是否仍在 prompt 前缀 | 长对话后请求医疗诊断，仍应触发免责声明 |
| 多意图状态共享 | `search → diet` 等多步任务后状态是否保留 | 先搜索食材，再让 diet 基于搜索结果推荐 |
| 工具 preview 控制 | 工具长结果是否被压成 preview，而非整段塞入 prompt | Tavily 返回多条长内容，只注入摘要 |
| 压缩触发稳定性 | 超过模型派生阈值时触发，未超过时不触发 | 构造触发线前后的字符/token 两组输入 |
| 摘要异常降级 | LLM 兜底输出格式错误时主流程不中断 | mock 一个不符合模板的摘要输出 |

### 14.2 核心指标

| 指标 | 判断方式 | 目标 |
|---|---|---|
| 关键事实保留率 | 压缩后 prompt / structured_state 是否包含 golden fact | MVP ≥ 80% |
| Prompt 超限率 | tokenize 后输入是否超过应用预算，且 `input + output` 是否超过模型硬上限 | 0 |
| 安全规则保留率 | 安全规则是否始终位于 prompt 前缀 | 100% |
| 压缩误触发率 | 未超过阈值却触发压缩的比例 | 尽量低，作为回归观察 |
| 压缩漏触发率 | 超过阈值却未触发压缩的比例 | 0 |
| 降级成功率 | LLM 摘要失败时主流程仍能返回 | 100% |

### 14.3 最小评测集

MVP 阶段不需要大规模 benchmark，建议先维护 20-30 条可解释 case：

- 8 条长对话事实保留 case
- 5 条安全规则保留 case
- 5 条多意图状态共享 case
- 5 条工具结果 preview case
- 3 条异常降级 case

每条 case 至少包含：输入轮次、预期保留字段、是否触发 compact、最终 prompt 长度、实际结果。

### 14.4 变强的判定

一次上下文压缩改动只有同时满足以下条件，才认为是正向优化：

- prompt 超限率没有上升。
- 安全规则保留率仍为 100%。
- 关键事实保留率提升，或在不下降的情况下显著降低 prompt 长度。
- LLM 摘要失败、工具结果过长、多意图链路等困难 case 不回退。

面试时可以这样讲：

> 我不会只看模型回答是否“像是对的”，而是把压缩拆成可测指标：关键事实有没有保留、安全规则有没有被截断、prompt 是否超限、异常摘要是否能降级。这样才能判断压缩策略是真的提升了上下文管理能力，而不是只是把历史对话变短。
