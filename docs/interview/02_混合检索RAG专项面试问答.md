# 混合检索 RAG 专项面试问答

> 对应简历亮点：围绕健身与健康饮食知识库，使用 BGE 向量、BM25、FAISS、RRF、父子分块和 RAGAS 建立可检索、可生成、可评测的 RAG 链路。
>
> 使用原则：先说“为什么需要这条链路”，再说“当前怎么实现、数据如何证明、边界在哪里”。文中的数字是 2026-08-08 父子索引 `v2` 的本地离线评测结果；当前实现已升级为 `v3-hierarchical`，尚未完成同口径复评，不能把旧数字包装成 v3 或线上生产指标。

## 1. 30 秒可直接回答

> 我的 RAG 不是只做向量搜索。当前按 Markdown 层级构造父子块：H2 形成主题父块，同主题 H3 与正文聚合，安全风险等硬边界独立，检索子块按 180/30 切分；查询时分别用 BGE Dense 和 BM25 各召回 20 个子块，用 RRF 做无量纲排名融合，再按父块聚合、补充上下文并输出 Top-5。SQLite 是可审计事实源，FAISS `IndexFlatIP` 是可重建的本地精确索引。评测上把检索和生成分开：上一版 `v2` 的 80 条检索集上 Hybrid Recall@5 为 0.967、MRR 为 0.893；RAGAS 在 tuning/holdout 上得到 `1.000/0.902/0.786` 和 `1.000/0.815/0.762`。当前 v3 只完成结构与兼容性验证，正式指标需要重建索引后复跑。

## 2. 90 秒项目展开

> 原始资料进入知识库后，系统保留章节标题和来源，以 H2 作为主题父块，在同一主题内聚合 H3 与正文叶子段；安全、风险等硬边界单独成父块，纯来源章节跳过。父块上限 500 字符，只有过长叶子段才按 500/80 切分，检索子块按 180/30 切分。这样既让子块适合精准检索，又能在命中后回到主题父块补齐语义。所有子块由 `BAAI/bge-small-zh-v1.5` 生成向量；SQLite 保存可审计文本和元数据，FAISS 对归一化向量做内积检索，BM25 则保留动作名、营养术语等精确词匹配能力。
>
> 在线查询时，Dense 和 BM25 各取 Top-20。二者原始分数不在同一尺度，所以不用直接加权分数，而用 RRF 根据名次计算 `1/(60 + rank)` 后累加；随后把同一父块下的重复子块折叠，回填父级上下文，最终返回 Top-5 给生成节点。生成模型被提示只基于检索上下文作答，资料不足时明确说明不足。
>
> 我没有把 RAGAS 分数和 Recall、MRR 混成一个总分。Recall@5 和 MRR 诊断 Retriever，RAGAS 的上下文相关性、忠实度和答案相关性诊断上下文质量与生成质量。当前 80 条样例包含 60 条可回答问题和 20 条 OOD，另把可回答集拆成 42 条 tuning 与 18 条 holdout，避免只报调参集。Hybrid 与 Dense 的 Recall@5 都是 0.967，但 Hybrid MRR 从 0.844 提升到 0.893，说明融合的主要收益是把正确内容排得更靠前，而不是增加已覆盖问题的数量。

## 3. 第一次出现的技术点

### 3.1 RAG、Retriever 与 Generator

- **是什么**：RAG（Retrieval-Augmented Generation，检索增强生成）先从外部知识库取回相关上下文，再让生成模型依据上下文回答。Retriever 是检索器，Generator 是生成器。
- **解决什么问题**：模型参数中的知识可能过时、不可追溯或覆盖不足；RAG 把可更新、可引用的项目知识在推理时注入模型，并降低无依据生成。
- **项目中怎么用**：用户进入知识问答链路后，Retriever 返回最多 5 个父级上下文，`generate_node` 把问题、上下文和回答约束交给 Qwen3-0.6B 或配置的在线模型生成答案。
- **类似方案**：模型微调、长上下文直接塞全文、联网搜索、知识图谱问答、工具调用。
- **为什么选择它**：健身知识有明确资料来源，需要低成本更新和可解释引用；相比微调，RAG 不必重新训练模型。最新资讯则走 Search 路由，不假装本地知识库实时更新。

### 3.2 分块、递归分块与父子分块

- **是什么**：分块把长文档切成可检索片段；递归分块按段落、句子等分隔符逐级切分；父子分块用较小子块负责命中、较大父块负责供给完整语义。
- **解决什么问题**：块太大时向量主题混杂，块太小时答案缺少限定条件；父子设计在“检索精度”和“生成上下文完整性”之间折中。
- **项目中怎么用**：保留 Markdown 标题栈，以 H2 形成主题父块并聚合同主题叶子段；安全风险等硬边界独立、纯来源章节跳过。父块上限 500 字符，检索子块为 180/30；命中子块后按 `parent_id` 聚合并回填父块。
- **类似方案**：固定长度切块、句子窗口、语义分块、文档摘要树、Late Chunking。
- **为什么选择它**：当前知识库是结构较清晰的专业资料，标题结构本身就是可靠信号；本地小模型环境下不额外引入昂贵且波动的 LLM 语义分块。

### 3.3 Embedding、Dense Retrieval 与 BGE

- **是什么**：Embedding 把文本映射成稠密向量；Dense Retrieval 用向量距离表示语义接近程度。BGE 是常用的文本嵌入模型系列。
- **解决什么问题**：用户不必和文档使用完全相同的词，例如“减脂时怎样保住肌肉”仍可召回包含“热量缺口和蛋白质摄入”的内容。
- **项目中怎么用**：`BAAI/bge-small-zh-v1.5` 为查询和子块编码，向量归一化后写入 SQLite 并同步到 FAISS。
- **类似方案**：E5、GTE、Qwen Embedding、OpenAI Embeddings、稀疏神经检索。
- **为什么选择它**：中文语义检索能力、模型体积和本地推理成本较平衡；当前没有用更大模型来制造不必要的部署负担。

### 3.4 稀疏检索与 BM25

- **是什么**：BM25 是基于词项匹配的概率排序方法。直觉上，查询词在文档中出现越有帮助，但收益会饱和；少见词权重更大；同时对过长文档做长度归一化。
- **解决什么问题**：向量语义检索可能忽略精确动作名、缩写、营养素名称和数字；BM25 对这些词面信号敏感。
- **项目中怎么用**：对子块建立 BM25 语料，查询时取 Top-20，与 Dense 候选做 RRF 融合。
- **类似方案**：TF-IDF、倒排索引、Elasticsearch/OpenSearch BM25、SPLADE。
- **为什么选择它**：知识库规模较小，本地实现足够轻量，且与 Dense 的错误模式互补。

### 3.5 FAISS、`IndexFlatIP` 与余弦相似度

- **是什么**：FAISS 是向量相似度搜索库；`IndexFlatIP` 对所有向量计算内积，不做近似剪枝。若向量先做 L2 归一化，内积就等价于余弦相似度排序。
- **解决什么问题**：避免每次用 Python 手工遍历并计算所有向量，同时提供统一的索引接口。
- **项目中怎么用**：SQLite 是事实源，FAISS 是派生索引；索引丢失或版本不一致时可以根据 SQLite 重建。
- **类似方案**：HNSW、IVF、Milvus、Qdrant、pgvector、Elasticsearch kNN。
- **为什么选择它**：当前只有小型本地知识库，Flat 精确搜索简单、无召回损失；上 HNSW 或独立向量数据库会增加当前阶段不必要的运维复杂度。

### 3.6 RRF 与 MRR

- **RRF 是什么**：Reciprocal Rank Fusion 是在线融合算法，对每个候选在各排行榜的名次累加 `1/(k + rank)`；项目中 `k=60`。它不依赖 Dense、BM25 原始分数可比。
- **MRR 是什么**：Mean Reciprocal Rank 是离线评测指标，对每个问题取第一个相关结果名次的倒数，再对所有问题求均值。
- **关键区别**：RRF 用来产生结果，MRR 用来评价结果；二者都出现倒数，但对象、目的完全不同。
- **类似方案**：加权分数融合、CombSUM、学习排序、Cross-Encoder 重排。
- **为什么选择 RRF**：实现稳定、可解释、无需额外标注训练，也避免直接混加不同尺度的 BM25 和余弦分数。

### 3.7 Recall@K、MRR、Gold Set 与 Holdout

- **Recall@K**：有相关结果的问题中，前 K 个是否至少命中一个；项目重点看 Recall@5。
- **MRR**：越接近 1，首个正确结果总体越靠前。它对第 1 名和第 2 名的差异比第 10 名和第 11 名更敏感。
- **Gold Set**：人工给定查询和预期相关文档/答案的评测集。
- **Tuning/Holdout**：tuning 用于调参数，holdout 留到最后验证，避免参数只记住已见样例。
- **项目中的限制**：80 条数据能减少极小样本的偶然性，但仍是自建离线集，不代表真实用户分布；需要持续加入同义改写、困难负例、跨主题问题和真实回放。

### 3.8 RAGAS 与三类生成指标

- **是什么**：RAGAS 是独立的 RAG 评测框架，支持用裁判模型判断检索上下文和答案质量。
- **解决什么问题**：字符串相等无法判断“意思对但写法不同”的答案，也无法直接量化幻觉和答非所问。
- **项目中怎么用**：本地 Qwen3-8B 量化模型作为离线裁判，分别计算上下文相关性、忠实度和答案相关性；在线生成模型不是这个 8B 裁判。
- **三个维度**：上下文相关性看检索上下文是否服务于问题；忠实度看答案中的陈述是否可由上下文支持；答案相关性看答案是否直接、完整回答原问题。
- **类似方案**：人工盲评、DeepEval、TruLens、ARES、自定义 LLM-as-a-Judge。
- **为什么选择它**：与检索指标形成互补，并可本地复现；但小型裁判可能偏置，所以必须人工抽检，不能把小数点当作绝对真值。

## 4. 当前完整链路

```text
权威资料 / 本地文档
  -> 清洗并保留标题、来源、文档标识
  -> 结构感知父块（约 500，overlap 80）
  -> 递归子块（约 300，overlap 50）
  -> BGE 生成并归一化子块向量
  -> SQLite 持久化文本、来源、向量、parent_id
  -> FAISS IndexFlatIP 构建可重建索引

用户问题
  -> BGE Dense Top-20
  -> BM25 Top-20
  -> RRF(k=60) 按排名融合
  -> 同父块聚合 / 回填父级语义
  -> Top-5 上下文
  -> generate_node 受控生成
  -> 返回答案、来源与降级信息

离线评测
  -> Retriever：Recall@5、MRR、Dense/Hybrid 对照
  -> Generator：RAGAS 上下文相关性、忠实度、答案相关性
  -> tuning / holdout 分拆 + 人工抽检
```

## 5. 高频问题与完整回答

### Q1：为什么一定要混合检索？只用向量不行吗？

**回答：**不是“一定要”，而是要用数据验证互补性。Dense 擅长同义表达和语义改写，BM25 擅长动作名、营养素、缩写等精确词面信号。当前结果里，两者的 Recall@5 都达到 0.967，Hybrid 没增加覆盖率，但 MRR 从 Dense 的 0.844 提高到 0.893，说明 BM25 和 RRF 主要把已命中的正确内容推到了更前面。这是当前保留混合检索的证据。如果将来更大真实集上没有稳定收益，我会简化链路，而不是为了技术名词强行保留。

### Q2：既然你的 RAG 本来就是混合检索，为什么还要单测 Dense？

**回答：**因为评测不仅要证明“最终系统能跑”，还要做归因。只报 Hybrid，无法知道收益来自向量模型、BM25、RRF，还是数据集太简单。Dense 是消融基线：Recall 不变而 MRR 上升，才说明融合改善了排序。如果 Hybrid 反而下降，我会检查 BM25 噪声、分词、RRF 参数或候选池，而不是盲目调生成模型。

### Q3：BM25 的公式你能解释吗？

**回答：**我不会在面试中死背所有符号，但会解释三个核心部分：第一是 IDF，越少见的查询词区分度越高；第二是词频饱和，同一个词出现 20 次不会比出现 10 次线性好一倍；第三是文档长度归一化，避免长文档因为词多天然占优。常见参数 `k1` 控制词频饱和，`b` 控制长度归一化。项目选择 BM25 是为了补 Dense 的精确词匹配，不是因为 BM25 能理解语义。

### Q4：RRF 为什么设为 60？调过吗？

**回答：**`k=60` 是原始 RRF 工作中常见且稳定的平滑设置，项目把它作为固定基线。k 越大，各名次间差距越平；越小越强调榜首。当前主要通过 Dense/Hybrid 消融和 holdout 验证融合收益，没有声称 60 是全局最优。进一步优化应在 tuning 上小范围搜索，再只用 holdout 做一次确认，避免在 holdout 上反复调参。

### Q5：为什么不直接把 Dense 分数和 BM25 分数加起来？

**回答：**余弦相似度和 BM25 分数的范围、分布、查询间稳定性不同，直接相加需要可靠归一化和权重标定。RRF 只看名次，可以避开分数尺度问题，而且实现简单、无训练数据依赖。代价是丢失了榜内绝对分差信息；数据量足够后可以尝试归一化加权或学习排序，并用 holdout 比较。

### Q6：父子分块比普通递归分块好在哪里？

**回答：**普通小块检索准但容易缺上下文，大块信息全但主题容易混杂。项目让子块承担“定位”，父块承担“阅读”。比如子块命中“减脂期蛋白质”，生成时会拿到包含适用条件和注意事项的父块，减少断章取义。但它也可能带入父块中的额外噪声，因此父块大小、同父块折叠和回填后的 Top-K 都需要评测。

### Q7：父块上限 500、子块 180/30 是最优的吗？

**回答：**不是理论最优，是结合中文资料结构、上下文预算和本地评测得到的工程基线。参数代表近似字符尺度而不是严格 token。优化时我会固定评测集，比较块大小、重叠、标题注入和父级回填策略，并同时看 Recall/MRR 与 RAGAS，防止只提高召回却让生成上下文更嘈杂。

### Q8：为什么用 SQLite 加 FAISS，数据不是重复了吗？

**回答：**职责不同。SQLite 保存可读文本、来源、向量、父子关系和稳定 ID，是事实源；FAISS 只负责高效向量搜索，是派生物。这样索引损坏时可重建，也便于审计和迁移。重复存向量增加了一点空间，但换来恢复能力和明确一致性边界。生产化可把元数据与向量放入 Milvus、Qdrant 或 pgvector，但当前单机规模不需要。

### Q9：为什么 `IndexFlatIP` 也能做余弦相似度？

**回答：**对向量先做 L2 归一化后，每个向量长度都是 1，此时两向量内积就是余弦相似度。因此项目使用 `IndexFlatIP` 排序。Flat 会逐个精确比较，复杂度随文档量线性增长；当前规模小，精确性和简单性优先。规模上升后才考虑 HNSW 或 IVF，并评估近似搜索造成的召回损失。

### Q10：Top-20 和最终 Top-5 是怎么确定的？

**回答：**Top-20 是每路候选池，让 Dense 和 BM25 有足够重叠与互补空间；Top-5 是最终给生成模型的上下文预算折中。候选太少会让融合无米下锅，最终上下文太多则增加噪声、延迟和 token。当前参数在离线集上固定验证，但并非生产最优；进一步应按问题类型自适应 K，或加入重排模型。

### Q11：同一个父块命中多个子块怎么办？

**回答：**项目按父块聚合，避免同一段内容占满 Top-5，同时回填父级语义。这能提高上下文多样性。当前仍要警惕两个实现边界：同标题不一定是同父块，必须以稳定 `parent_id` 为准；折叠后如果条数不足，应该从后续候选补位。面试时我会把这说成已识别的优化点，而不是假装所有边界都已生产化。

### Q12：Recall@5=0.967 算好吗？

**回答：**对当前自建离线集是较好的覆盖率，约等于 60 个可回答问题中大部分能在前 5 找到相关内容；但不能脱离数据集下结论。要看标注质量、问题难度、知识库覆盖和置信区间。80 条比最初小样本更稳，但仍不足以代表线上长尾，因此我的表达是“当前离线基线较高”，不是“检索已达到生产水平”。

### Q13：MRR=0.893 怎么理解？

**回答：**它表示每个问题首个相关结果名次倒数的平均值。0.893 很接近多数问题把相关内容排在第一位，但不能直接反推出确切的第一名比例。MRR 只关注第一个相关结果，不评价第二、第三个相关上下文是否全面，所以还要配合 Recall@K、人工检查和生成指标。

### Q14：RAGAS 三个分数说明了什么？

**回答：**tuning 的上下文相关性/忠实度/答案相关性为 1.000/0.902/0.786，holdout 为 1.000/0.815/0.762。检索上下文在这批可回答问题上高度相关，但 holdout 忠实度下降，说明生成答案有些表述不能充分从上下文支持；答案相关性约 0.76，说明还存在回答不够直接或不够完整。下一步不应继续只调 Retriever，而应抽查低分答案、收紧提示词、改善引用和不足回答策略。

### Q15：上下文相关性为什么能到 1.000，会不会评测失真？

**回答：**可能有两个原因：数据集问题与知识块主题较集中，或者本地裁判区分度有限。因此我不会把 1.000 当成绝对完美。需要人工抽查上下文、加入相似但错误的困难负例，并用更强裁判或少量人工标注校准。LLM-as-a-Judge 是自动化近似，不是权威真值。

### Q16：为什么 holdout 忠实度低于 tuning？

**回答：**这正是拆分 holdout 的价值。可能是 holdout 问题措辞更陌生、需要组合多个上下文，或者生成模型补入了常识性表述。正确做法是逐条看 claim 与证据，不在 holdout 上直接反复调参；将发现的错误模式抽象成新规则或新训练样例，再建立下一版独立 holdout。

### Q17：你的 RAGAS 裁判模型为什么用 Qwen3-8B？它和在线模型是什么关系？

**回答：**Qwen3-8B 的量化版本只用于离线语义评测，原因是中文能力、可本地运行和不依赖外部 API；在线回答当前主要使用更轻的 Qwen3-0.6B 或配置模型。裁判与选手分开能减少完全自评，但同系列仍可能有偏置，所以项目保留人工复核边界，也不把 RAGAS 当唯一发布门槛。

### Q18：OOD 样例怎么评？

**回答：**OOD 是知识库无法可靠回答的问题，目标不是召回某个“正确文档”，而是检验系统能否识别证据不足、避免硬答。当前 80 条集中有 20 条 OOD，检索 Recall/MRR 主要在 60 条可回答问题上计算；OOD 另看拒答、降级和是否错误引用。把它们硬塞进 Recall 分母会混淆“知识缺失”和“检索失败”。

### Q19：怎么降低 RAG 幻觉？

**回答：**分四层：数据层保留来源和清晰分块；检索层设相关性与 OOD 处理；提示层要求只依据上下文、证据不足则说明不足；输出层附来源并用忠实度评测抽查。生产化还可做逐句引用、claim-evidence 校验或二次审校。不能承诺完全消除幻觉，只能提高可检测和可降级能力。

### Q20：为什么没有 Cross-Encoder 重排？

**回答：**Cross-Encoder 同时读 query 和候选文本，通常比单向量相似度更精细，但每个候选都要额外前向推理。当前 RRF 已在本地集上把 MRR 提到 0.893，项目优先保持可运行和可讲解，所以还未引入。最有价值的下一步是对 RRF 后的 20～40 个候选做轻量重排，并用相同 holdout 验证收益、延迟和内存成本。

### Q21：知识更新后如何保证 FAISS 与 SQLite 一致？

**回答：**用稳定块 ID 和索引版本记录构建批次；SQLite 先完成事实写入，再生成或重建 FAISS。启动时检查数量、模型版本和维度，不一致就把索引视为失效并重建。当前项目具备“事实源与派生索引”的设计，但还不是分布式事务；生产环境需要原子切换索引版本、后台构建和回滚。

### Q22：如果知识库扩大一百倍，你会怎么改？

**回答：**先测瓶颈再替换：BM25 迁到 Elasticsearch/OpenSearch，向量检索改用 HNSW/IVF 或 Milvus/Qdrant；增量构建索引并按版本原子切换；增加元数据过滤、权限过滤和 Cross-Encoder 重排；监控延迟、空召回率、Recall、MRR、引用正确率及成本。不会因为“数据大”就同时替换所有组件。

### Q23：RAG 和联网搜索是什么关系？

**回答：**本项目的 RAG 面向经过整理的健身与饮食知识库，强调稳定来源和可复现评测；Search 子图面向“最新研究、近期资讯”等时效问题。Router 会根据时效信号选 Search。二者可以在生产化中统一做证据合成，但当前边界清楚，避免把陈旧本地文档冒充最新信息。

### Q24：RAG 链路最大的当前风险是什么？

**回答：**不是 Recall 不够，而是评测分布和生成可靠性。现有检索集仍由项目自建，RAGAS 裁判也只是本地 8B 模型；holdout 忠实度 0.815 已提示生成存在可改进问题。另外，健康建议必须避免诊断化和绝对承诺。我的优先级会是人工复核低分样例、补困难负例和证据引用，再考虑更复杂索引。

## 6. 面试官连续追问示例

### 追问链 A：从“混合检索”追到“指标归因”

1. 为什么混合？——Dense 管语义，BM25 管精确词。
2. 怎么融合？——RRF 按名次融合，避免分数尺度不一致。
3. 怎么证明有效？——与 Dense 做消融，Recall 持平、MRR 提升约 0.049。
4. 为什么 Recall 没提升还保留？——正确证据更靠前，减少生成节点看到噪声；同时继续在 holdout 检查是否稳定。
5. 会不会过拟合？——调参与 holdout 分开，下一版加入真实回放和困难负例。

### 追问链 B：从“RAGAS”追到“裁判可信度”

1. RAGAS 是什么？——RAG 专项自动评测框架。
2. 谁来打分？——本地 Qwen3-8B 量化裁判。
3. 裁判会不会错？——会，所以做人工抽检、困难负例和独立 holdout。
4. 为什么不只看答案相关性？——答对问题不等于有证据；还要看忠实度和上下文。
5. 能否合成总分？——技术上能，但会掩盖问题归因，当前刻意分开报告。

### 追问链 C：从“本地原型”追到“生产化”

1. 为什么 SQLite+FAISS？——单机、简单、可重建。
2. 并发和大规模怎么办？——迁移到服务化稀疏/向量索引。
3. 如何更新？——版本化增量构建、原子切换、可回滚。
4. 如何监控？——延迟、空召回、Recall/MRR、引用正确率、忠实度和拒答率。
5. 如何保障健康安全？——来源白名单、风险分类、证据不足拒答和人工升级。

## 7. 容易露馅的说法与正确口径

| 不要这样说 | 建议这样说 |
|---|---|
| “RAGAS 证明答案完全正确。” | “RAGAS 是本地裁判的自动化近似，需结合人工抽检。” |
| “FAISS 就是向量数据库。” | “FAISS 是向量索引库；项目用 SQLite 负责持久化事实。” |
| “用了 RRF，所以 MRR 高。” | “RRF 是融合方法，MRR 是离线指标；消融显示当前集上有提升。” |
| “Recall 0.967，系统已经很好。” | “这是自建离线集上的较高基线，不代表线上泛化。” |
| “父子分块是 LLM 语义分块。” | “当前是标题结构感知加递归分块，不调用 LLM 做语义边界判断。” |
| “Qwen3-8B 负责在线回答。” | “8B 是离线 RAGAS 裁判；在线生成主要是 0.6B 或配置模型。” |
| “项目已经用了重排模型和向量数据库。” | “Cross-Encoder 和服务化向量库是数据规模扩大后的升级方向。” |

## 9. 当前边界与生产化升级

### 当前已经实现

- 结构感知父子分块、BGE Dense、BM25、RRF、父级聚合和 Top-5。
- SQLite 事实源与 FAISS 可重建向量索引。
- 80 条检索集、Dense/Hybrid 消融、tuning/holdout 拆分。
- 本地 Qwen3-8B RAGAS 三维评测链路。

### 当前没有实现

- LLM 语义分块、Cross-Encoder 重排、在线向量数据库。
- 大规模真实流量评测、人工双盲标注平台、严格置信区间。
- 完整逐句引用验证和生产级权限隔离。

### 生产化优先级

1. 人工复核 holdout 低忠实度/低相关性案例并补困难负例。
2. 加入轻量 Cross-Encoder，验证 MRR、RAGAS 与延迟净收益。
3. 建立索引版本、增量构建、原子切换与回滚。
4. 数据规模和并发达到阈值后再迁移服务化检索引擎。
