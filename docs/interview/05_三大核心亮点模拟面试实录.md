> 对应简历亮点：混合意图路由、混合检索 RAG、分层记忆与上下文压缩。
>
> 记录方式：每次只进行一道题。用户回答后，再补充回答评估、参考答案和关键差异；用户确认理解后进入下一题。总题量控制在 10 题左右，并根据实际薄弱点调整追问深度。

## 第 1 题：混合意图路由完整链路

### 面试官提问

你在简历中写了“构建可评测的混合意图路由”。请你从用户请求进入系统开始，完整讲一下它如何得到最终执行计划，并重点说明：系统怎样区分单意图、明确的多意图和存在歧义的候选竞争？

### 你的回答

首先系统接收用户的输入，会对用户的意图进行识别。这个识别分为三层，第一层是关键词加权得分，每一个意图都内置了若干关键词，不同关键词有不同得分，这里就分为几种情况，第一种只有一种意图得分大于 3 分，那么会直接执行单意图；如果两个意图大于 3 分，就需要看它们的得分差值以及最高得分是多少。如果主意图得分远高于次意图，那么次意图就会被识别为噪声；如果意图得分很接近，而且存在明确的连接词，比如“先……再……”或者“同时……”之类的，就会被识别成多意图，并按顺序执行。但是如果没有，就会被系统判断存在歧义，系统会弹出提示，让用户自行选择是执行某个单意图还是多意图。

如果没有意图达到得分阈值，就会进入下一层，即通过 Embedding 模型进行语义识别。每个意图都有二十余条例句，系统提前将这些句子编码成向量；当第一层没能完成匹配时，也把用户输入编码成向量，再与已有样例向量计算余弦相似度，越接近哪一类，就越可能属于哪一种意图。最后一层是最终兜底，如果前两层都没完成意图识别，就使用大模型再判断一次用户意图。

### 回答评估

**面试表达：85/100；当前代码防守性：65/100；综合：75/100。**

这段回答的主线清楚，也基本覆盖了简历项目描述中的“加权规则 + 语义样例匹配 + LLM 兜底”，作为面试开场回答是成立的。优点包括：

- 解释了三级、按需兜底的总体思路。
- 能区分单意图、次意图噪声、明确复合任务和候选歧义，而不是机械地选择最高分。
- 讲清了 Embedding 样例预编码和余弦相似度匹配的基本原理。
- 知道复合任务需要形成执行顺序，真正不确定时应让用户确认。

需要修正的逻辑点：

1. **多意图的核心证据不是“两个分数接近”。** 分数接近只说明两个候选竞争激烈；文本中确实存在两个可独立执行的任务，并有“先 A 再 B”“A 同时 B”等组合结构，才说明是明确多意图。没有组合结构时，接近的得分更可能触发澄清。
2. **Embedding 不能只说“最接近谁就是谁”。** 还应设置接受门槛和 Top1、Top2 分差门槛，否则任何无关输入都会被强行归到某一类。
3. **LLM 兜底也要有边界。** 应限制它只能从既定意图枚举中返回结构化结果，并保留低置信拒识或澄清出口，不能把模型输出直接当成可执行命令。
4. **“弹出提示”不够准确。** 更专业的表达是“返回针对性的澄清问题，并保存待决路由状态”；用户下一轮选择后，系统恢复原请求对应的路由。
5. 阈值应说“**大于等于 3 分**”，并说明 3 分是通过回归样本校准的工程阈值，不是概率。

#### 包装与过度包装风险

- **三级路由默认在线运行：高风险。** 当前代码确实保留了规则、Embedding 和 LLM 三段式接口，但 Embedding 与 LLM Router 默认关闭，默认主链路是确定性混合信号路由。因此不能在深入追问时坚持“生产主链路现在一定逐层调用三者”。更稳妥且更有工程判断力的说法是：“架构上实现了可开关的三级级联；当前默认使用经过回归验证的确定性主链路，Embedding 和 LLM 作为实验兜底，按评测收益决定是否开启。”
- **每类二十余条例句：明显过度包装。** 当前 `SEMANTIC_EXAMPLES` 每类只有约 5～7 条，总计约 30 条，不是每类二十余条。这个数字很容易被追问“样本从哪里来、如何划分训练集和测试集”，必须改为“每类维护少量代表样例”，或者先真实补齐数据再说二十余条。
- **纯关键词加权：轻微失真。** 当前规则层不只有关键词，还包含组合模式、文件/工具信号、否定约束和顺序/并列信号。只说关键词会低估亮点，也容易让面试官认为它只是大量 `if/else`。
- **用户选择后立即恢复：已实现且可防守。** 但回答遗漏了“保存原请求、候选意图和待决状态”，没有把简历中的“跨轮恢复”讲出来。

### 参考答案

我把路由设计成可开关的三级级联结构。第一层是确定性的混合信号路由：先对输入做基础归一化，再综合加权关键词、组合模式、文件或工具信号、否定约束以及顺序表达，为搜索、动作分析、饮食建议等候选意图计分。候选达到 3 分门槛后，不是简单取最高分，而是结合最高分、Top1 与 Top2 的分差和句子结构形成执行计划。

如果只有一个可靠候选，或者主意图明显高于其他候选，就执行单意图，低分候选按噪声处理；如果文本中明确包含两个可独立执行的任务，并出现“先 A 再 B”或“A 同时 B”这样的组合关系，就生成受控的多意图计划，并按用户表达的顺序执行；如果两个候选都很强，但文本不足以判断用户究竟想执行哪一个或是否都执行，就先不调用业务子图，而是生成包含具体候选的澄清问题，同时保存原始请求和待决路由。用户下一轮回答后，系统解析其选择并恢复原任务。

规则层无法形成可靠结论时，架构上可以开启轻量 Embedding 样例匹配：预先把每类少量代表样例编码成向量，在线计算用户输入与样例的余弦相似度，只有最高相似度及其相对第二名的优势都达到门槛才接受。仍不可靠时，再通过受约束的 LLM 分类器兜底，要求它只能从既定意图集合中返回结构化结果；低置信结果继续澄清或安全回退。

当前默认主链路采用经过离线回归验证的确定性混合信号路由，Embedding 和 LLM 作为可开关的实验层保留，因为兜底模型是否值得在线启用要看它对长尾样本的增益、延迟和误判成本。最终计划还会经过合法意图、去重、数量和顺序校验，再交给 LangGraph 对应子图执行。这样既有规则的可解释和可约束，也保留了语义泛化的演进空间，并能通过常规、困难和语义改写集持续回归。

- 你的三级路由结构与简历项目描述一致，但把可选实验层说成了默认在线链路，深入追问时有暴露风险。
- 你把规则层缩成了关键词加权，遗漏了组合模式、文件信号、否定约束等真正体现“混合”的部分。
- 你把分数接近和多意图绑定得过紧；正确关系是分数负责候选竞争，明确的双任务结构负责证明多意图。

- 你提到让用户选择，但没有说明如何保存待决状态并在下一轮恢复原请求。
- “每类二十余条”与当前代码不符，应降为“每类少量代表样例”。

### 第 1 题追问：Embedding 分差门槛是否与规则层相同

**用户提问：** Embedding 不能简单说“最像哪个就是哪个”，还要经过相似度和 Top1、Top2 分差门槛。这里的分差门槛具体是多少？和第一层是一样的吗？

**回答：** 不一样。Embedding 路由当前默认要求 Top1 与 Top2 的余弦相似度分差 `margin >= 0.05`，同时由 Top1 相似度和分差计算出的综合置信度必须 `>= 0.68`。其计算式为 `0.50 + Top1 × 0.35 + margin × 0.35`，最高封顶为 `0.92`。当前代码并没有再设置一个独立的“Top1 余弦相似度最低值”，因此面试时更准确的说法是“综合置信度门槛和 Top1-Top2 分差门槛”，而不是“Top1 相似度门槛”。

第一层规则路由使用的是另一套量纲：候选意图首先要达到加权规则分 `3.0`；当两个以上候选都过线且没有明确的顺序或并列结构时，再把最高规则分和规则分差合成为工程置信度，置信度达到 `0.80` 才把第二意图视为噪声并选择单意图，否则进入澄清。规则层没有一个与 `0.05` 对应的固定原始分差门槛，所以两层数值不能直接比较。

### 第 1 题追问：Top1 相似度与 Embedding 判断链路

**用户提问：** Top1 相似度是什么？和余弦相似度有什么关系？具体 Embedding 是怎么进行判断的？

**回答：** Top1 相似度不是独立的相似度算法，而是余弦相似度计算结果中的最高分。系统预先将每个意图的代表样例编码为向量；在线把用户输入编码为同一向量空间中的向量，并与每条样例计算余弦相似度。当前实现先为每个意图保留其最相似样例的分数，再对五类意图排序：最高的意图分数叫 Top1，相邻第二名叫 Top2，二者差值叫 margin。

例如用户输入与各类最相似样例的分数分别是：`diet=0.82`、`chat=0.71`、`search=0.40`、`motion=0.35`、`mcp=0.30`，那么 Top1 是 `diet=0.82`，Top2 是 `chat=0.71`，分差为 `0.11`。当前默认门槛要求综合置信度至少 `0.68` 且分差至少 `0.05`，两项都满足才接受 `diet`；否则拒绝本层结果，继续进入后续兜底。该层是“每类取最近代表样例后再竞争”的单意图分类，不是多数投票，也不负责生成多意图计划。

## 第 2 题：歧义澄清与跨轮路由恢复

### 面试官提问

假设用户输入同时命中了“饮食建议”和“知识搜索”，两个候选都比较强，但句子中没有明确说明是只执行一个还是两个都执行。你的系统为什么不会直接选择最高分？它会怎样生成针对性的澄清问题？如果用户下一轮只回答“第一个”“都要”或者“我想问饮食”，系统又是如何找回上一轮原始请求并恢复正确路由的？请把状态保存、答案解析、恢复执行和异常兜底的完整链路讲清楚。

### 你的回答

这里系统就会判断存在歧义，所以不会直接选择最高分，系统会先把意图都列出来。因为多意图最多是两个，所以最多也就三个选项，两个单意图和组成的多意图让用户进行选择。当用户选择了相应的意图，系统会直接执行，同时由于系统对会话记忆的处理是保留最近六轮的原文，所以很轻易地能拿到用户上一轮的原始请求。

### 回答评估

**面试表达：75/100；当前代码防守性：60/100；综合：68/100。**

回答抓住了“不确定时不强行选择最高分”和“允许用户在两个单意图及组合任务之间选择”这两个核心点。候选最多取前两个，澄清模板提供“前者、后者、两个都要”三种决策方向，这部分逻辑成立。

主要问题是把跨轮恢复错误地归因于“最近六轮原文”。当前实现并不依靠模型回看短期对话并猜测上一轮问题，而是建立了独立的待决路由状态：普通会话按 `user_id + conversation_id` 将原始问题、两个候选、澄清问题和候选分数写入 SQLite `task_states`；下一轮请求进入 Router 前先读取该状态。这样即使服务重启，也能恢复原任务，并且不会把不同用户或不同会话的待决任务串在一起。临时会话才只保存在进程内存中。

还遗漏了三个容易被追问的细节：

1. 澄清问题由确定性模板生成，不额外调用 LLM，也不会在澄清轮提前执行候选业务子图。
2. 用户回答支持序号、前者/后者、意图名称别名和“两项都要”；选择成功后生成新的受控执行计划，并把原问题与澄清答案组合后交给对应子图。
3. 用户回复“取消/不用了”会清除待决状态；如果输入了一个足够明确的新任务，就按新任务路由并清除旧状态；如果既不是有效选择，也不是明确新任务，则再次返回澄清问题并继续保留状态。解析成功或取消后，待决状态都会删除，防止影响后续对话。

#### 包装与过度包装风险

- **“最多三个选项”：基本合理。** 当前交互实际展示两个候选，并通过文字提供“两项都要”；面试中可以概括为三种决策方向，但不要说前端一定渲染了三个独立按钮。
- **“依靠最近六轮原文恢复”：不是包装，而是技术归因错误。** 如果面试官追问后端重启、跨会话隔离或摘要替换原文，就会立即暴露矛盾。必须改为依靠独立持久化的待决任务状态。
- **“用户选择后直接执行”：需要补充约束。** 不是把用户文本直接当执行命令，而是先解析为候选白名单内的路由计划，再经过计划校验，最后交给 LangGraph 对应子图执行。

### 参考答案

当两个候选意图都超过规则门槛、主次差距不足以安全选择，而且文本中又没有明确的顺序或并列结构时，系统不会直接取最高分，也不会提前执行任何业务工具，而是进入澄清节点。澄清节点用确定性模板列出前两个候选的名称和含义，让用户选择第一个、第二个或两个都要，因此不需要额外消耗一次 LLM 调用。

为了支持跨轮恢复，系统会把原始问题、两个候选意图、候选分数和澄清问题保存成独立的 `route_clarification` 状态。普通会话按用户和会话维度写入 SQLite 的 `task_states`，临时会话才使用进程内状态。所以下一轮并不是依赖最近六轮对话让模型猜，而是在请求进入 Router 前精确加载待决状态。

用户下一轮回复后，系统先进行确定性解析：`1/第一个/前者` 选择第一个候选，`2/第二个/后者` 选择第二个候选，能力名称可以按别名匹配，`两个都要/一起做` 则恢复为最多两个步骤的多意图计划。解析成功后，系统将原始问题与本轮澄清答案组合起来，构造白名单内的执行计划，再交给对应 LangGraph 子图执行，并立即清除待决状态。

如果用户回复“取消、算了、不用了”，系统清除旧状态；如果用户没有回答选项，而是提出一个可以独立可靠识别的新任务，系统放弃旧澄清并执行新任务；如果答案仍然无法解析，就重新提示两个候选并继续保留待决状态。这样形成了“发现歧义—暂停执行—保存状态—用户确认—恢复路由—清理状态”的完整闭环。

### 你的回答

首先，模型会带着用户的问题去知识库进行搜索，Embedding 模型会把用户的问题转换成向量，通过和向量数据库中的向量进行余弦相似度对比，找到最相近的知识库片段。这里会使用密集向量和稀疏向量综合的混合检索，两路各取 Top20，再进行 RRF，也就是倒数排序融合，最后得到 Top5 作为最终匹配的知识库结果。

1. **不是“模型带着问题搜索”，而是检索节点先执行搜索。** LangGraph 将请求路由到 Chat 或 Diet 子图后，检索节点通过统一的 `knowledge.retrieve` 工具调用检索器；Embedding 模型只负责把查询编码成向量。检索证据组装进 Prompt 后，运行时 LLM 才负责生成答案。这样说能明确区分检索模型和生成模型。

### 追问：SQLite 和 FAISS 分别是什么，为什么要同时使用

#### 问题

SQLite 适合长期存储内容，那么 FAISS 是什么、具体承担什么作用？项目为什么需要同时使用 SQLite 和 FAISS？

#### 正确答案

SQLite 和 FAISS 解决的不是同一个问题，可以把它们理解成“仓库档案”和“快速定位目录”。

- **SQLite 负责可靠持久化。** 它保存知识子块的原文、来源、章节路径、父块编号、父级正文、内容哈希以及 Embedding 向量。程序退出或电脑重启后数据仍然存在，也便于查询元数据、替换某个来源和重新构建索引。
- **FAISS 负责向量相似度搜索。** FAISS 是面向高维稠密向量的相似性搜索库。用户问题被 Embedding 模型转换成向量后，FAISS 根据向量距离快速找出语义最相近的知识子块。它擅长的是向量检索，不负责完整的业务数据管理、来源查询和长期持久化。
- **两者通过稳定记录顺序建立对应关系。** 项目从 SQLite 读取已持久化的知识记录和向量，在进程内构建 FAISS 索引；FAISS 返回向量位置后，系统再从对应记录中取得正文、来源和父块信息。SQLite 中的向量和元数据是可恢复的事实源，FAISS 是可随时重建的查询加速结构。

当前使用的 FAISS `IndexFlatIP` 是精确内积索引。知识向量和查询向量在搜索前都经过 L2 归一化，因此内积排序等价于余弦相似度排序。项目数据规模较小时，精确索引实现简单、结果稳定，也没有近似索引的召回损失；如果未来知识规模明显扩大，可以再替换为 IVF、HNSW 等近似索引。

如果只使用 SQLite，可以把向量以 BLOB 形式存下来，但普通 SQLite 不擅长直接计算和排序大量高维向量的相似度；应用层逐条读取计算虽然能够实现，却会随着数据规模增大而变慢。如果只使用 FAISS，虽然能完成向量搜索，但知识原文、来源、章节和父子关系的管理不方便，而且进程内索引需要有可靠数据来源才能在重启后恢复。因此项目选择 SQLite 负责“保存和管理”，FAISS 负责“计算和检索”。

#### 面试口述版

SQLite 和 FAISS 在项目中是互补关系。SQLite 是持久化事实源，保存知识块正文、来源、父子关系和向量，保证重启后仍能恢复；FAISS 是专门做高维向量相似度搜索的库，用户问题向量化后，由它快速找到语义最接近的子块。项目启动时可以从 SQLite 读取向量重建 FAISS 索引，FAISS 返回命中位置后，再关联回 SQLite 记录取得正文和来源。简单说，SQLite 解决“数据怎么可靠保存”，FAISS 解决“向量怎么高效搜索”。

### 追问：FAISS 是否类似 Milvus 向量数据库

FAISS 和 Milvus 都能完成向量相似度检索，但不属于同一层级。FAISS 更准确地说是一个向量检索算法库或索引引擎，主要提供 `Flat`、`IVF`、`HNSW` 等索引及最近邻搜索能力；它不直接提供完整的数据库服务、业务元数据管理、网络接口、权限、集群扩缩容和分布式持久化能力。Milvus 是完整的向量数据库系统，在向量索引之上还提供 Collection、Schema、标量过滤、持久化、服务端接口、权限及分布式部署等数据库能力，其底层也需要使用向量索引算法完成搜索。

因此可以说“FAISS 和 Milvus 都能用于向量检索”，但不能把 FAISS 直接称为 Milvus 同级的向量数据库。当前项目使用 `SQLite + FAISS`，实际上是用 SQLite 补齐数据持久化和元数据管理，用 FAISS 完成向量搜索，以较低部署成本组合出适合本地单机原型的轻量向量存储方案；如果知识规模、并发量和多机部署需求增长，再迁移到 Milvus 更合理。

#### 继续追问：SQLite 与 FAISS 相加是否等于 Milvus

在本项目的单机 RAG 范围内，可以说 `SQLite + FAISS` 共同覆盖了 Milvus 最核心的两项用途：SQLite 负责持久化知识、向量和元数据，FAISS 负责向量相似度检索。但是这只是功能子集，不能写成二者相加就完整等于 Milvus。

Milvus 还提供服务端 API、Collection 与 Schema 管理、向量和标量的组合查询、并发访问、权限、索引生命周期、数据分片、副本、集群扩缩容和分布式容错等数据库能力。这些都不是简单组合 SQLite 与 FAISS 后自动获得的。准确口径是：当前项目用两个轻量组件满足本地原型所需的“持久化 + 向量检索”，避免为小规模知识库引入独立的 Milvus 服务；规模和运维要求上升后，再使用 Milvus 取代这套组合。

### 基础讲解

RAG 有两个可能独立出错的阶段，所以需要两层评测：

1. **检索层：知识有没有找到、正确证据排得是否靠前。** `scripts/eval_retrieval.py` 不调用生成模型，只让 Dense 或 Hybrid 检索器处理带有预期来源标注的黄金问题。Recall@5 检查前五条里是否至少出现一条正确证据；MRR 根据第一条正确证据的排名计算倒数并对全部样例取平均。第一条排第 1、2、5 名分别贡献 `1`、`1/2`、`1/5`，没有命中贡献 `0`。
2. **生成层：拿到证据后，最终回答是否可用。** `scripts/eval_rag.py` 让样例经过真实 Retriever 和项目生成节点，再由 RAGAS 的三个 scorer 评估：上下文相关性检查检索上下文与问题是否相关；忠实度把回答拆成事实并检查是否受上下文支持；答案相关性检查回答是否真正围绕用户问题。这条链路会调用生成模型和离线裁判，成本与波动都高于纯检索评测。

两层不是重复关系。Recall@5 和 MRR 使用人工标注的预期证据，便于低成本定位检索问题；RAGAS观察检索上下文与真实生成答案之间的端到端表现。检索命中但回答忠实度低，通常说明生成模型没有正确使用证据或发生了扩写；检索遗漏时，生成评分再好也不能证明系统掌握了缺失知识。当前 RAGAS 三项没有直接拿黄金 `reference` 计算标准答案正确率，因此不能把它们包装成“回答正确率”。

父子索引 v2 的 60 条可回答样例中，Dense 与 Hybrid 的 `Recall@5` 都是 `58/60=0.967`，说明混合检索没有增加 Top5 内至少命中一次的样例数；MRR 从 Dense 的 `0.844` 提高到 Hybrid 的 `0.893`，绝对增加 `0.049`，相对约提高 `5.8%`，说明混合检索主要把正确证据排得更靠前。它不能单独证明最终答案质量提升。

生成层将 60 条可回答样例分为 42 条 tuning 和 18 条 holdout。三项 RAGAS 按“上下文相关性 / 忠实度 / 答案相关性”的顺序，tuning 为 `1.000/0.902/0.786`，holdout 为 `1.000/0.815/0.762`。tuning 可以用于调整分块、召回和 Prompt；holdout 应在方案确定后用于验证未参与调参的数据，避免反复看同一批样例后把记住测试集误当成泛化能力。holdout 的后两项下降也提示生成链路仍有改进空间。

这些数字全部属于父子索引 v2。当前 v3 层级聚合已经通过结构与检索兼容性测试，但尚未完成正式索引重建和同口径复评，因此不能把 v2 数字写成 v3 的提升，也不能把小规模离线结果说成生产环境准确率。

### 追问：Recall、MRR 与 RAGAS 是否可以理解为检索层和应用层评测

用户理解为：Recall 和 MRR 关注 RAG 的检索质量，而 RAGAS 还会关注模型拿到检索结果后的运用质量。

这个方向正确，但需要补充一个边界：Recall@5 和 MRR 是典型的检索层指标，分别关注 Top5 是否命中正确证据，以及第一条正确证据排得是否靠前；RAGAS 更接近端到端质量评测，其中上下文相关性仍会评价检索到的上下文，忠实度和答案相关性才进一步评价模型是否依据证据作答、是否回答了用户的问题。因此两套评测有少量交叉，但分工不同：检索指标更适合精确定位 Retriever 的排序问题，RAGAS 更适合观察“检索结果交给模型以后，最终回答是否可用”。

面试时可以简洁表述为：

> Recall@5 和 MRR 主要评价检索器能不能找到正确证据、能不能把它排在前面；RAGAS 则进一步评价检索上下文是否相关，以及模型是否忠实地利用这些上下文回答了用户问题。因此前者负责定位检索质量，后者更接近端到端回答质量，两者互补而不是重复。

### 评价指标的详细记忆框架

可以把完整 RAG 想成“资料员找资料，再由答题人组织答案”：

1. `Recall@5` 问资料员：前五份资料里有没有正确证据？
2. `MRR` 继续问资料员：第一份正确证据排在第几位？
3. RAGAS 的上下文相关性问：取回来的整批资料与问题相关吗？
4. RAGAS 的忠实度问答题人：回答中的事实有资料支持吗？
5. RAGAS 的答案相关性问答题人：回答是否真正回答了用户的问题？

#### 1. Recall@5：有没有找到

当前项目对每条可回答样例都标注了预期来源和关键证据片段。检索 Top-5 后，只要其中至少一条同时匹配预期来源和证据片段，这个问题就记为命中，否则记为未命中；最终用命中问题数除以可回答问题总数。

例如 60 个可回答问题中有 58 个在 Top-5 内命中，`Recall@5=58/60=0.967`。它不关心正确证据排第 1 还是第 5，也不评价模型最终怎样回答。严格的学术 Recall 常按“召回的相关文档数 / 全部相关文档数”统计；本项目是一题至少命中一条黄金证据的 hit-style Recall，因此面试时应直接解释算法，不必把口径夸大为找全了所有相关资料。

#### 2. MRR：第一条正确证据排得多靠前

MRR 全称 Mean Reciprocal Rank，即“平均倒数排名”。每个问题只看第一条正确证据：排第 1 得 `1` 分，排第 2 得 `1/2` 分，排第 5 得 `1/5` 分，没有命中得 `0` 分，最后对全部可回答问题取平均。

因此 Recall@5 相同并不代表排序相同。例如两个检索器都在 Top-5 找到了正确证据，但一个通常排第 1，另一个通常排第 5，前者 MRR 会明显更高。父子索引 v2 中 Dense 与 Hybrid 的 Recall@5 都是 `0.967`，而 MRR 从 `0.844` 提高到 `0.893`，说明混合检索没有扩大 Top-5 问题覆盖，但让第一条正确证据总体更靠前。

#### 3. RAGAS：框架名称，不是单个指标

RAGAS 是 RAG 评测框架。本项目从中选择了三个评分维度，通常在 `0—1` 之间，越高越好：

- **上下文相关性（Context Relevance）**：输入是用户问题和检索上下文，判断取回来的上下文与问题是否相关、噪声是否过多。它仍会涉及检索质量，但不像 Recall@5、MRR 那样依赖项目标注的黄金证据位置。
- **忠实度（Faithfulness）**：输入是问题、检索上下文和生成答案，检查回答中的事实主张能否得到上下文支持。它主要发现模型脱离证据扩写或产生幻觉。回答切题但编造内容时，答案相关性可能不低，忠实度却应较低。
- **答案相关性（Answer Relevance）**：输入是用户问题和生成答案，判断答案是否围绕问题、是否真正答到点上。回答完全依据资料但答非所问时，忠实度可能较高，答案相关性仍会较低。

本项目当前三个 RAGAS 指标没有直接使用黄金标准答案进行比对，因此不能把它们称为“答案准确率”。它们也不应与 Recall@5、MRR 加权合成一个总分；出现问题时，应结合各指标定位是检索遗漏、排序靠后、上下文噪声、模型幻觉还是答非所问。

#### 4. 辅助指标和容易混淆的名词

- **无答案空结果率**：对知识库无法回答的问题，检查 Retriever 是否返回空结果。当前它只说明检索器是否克制，不能直接称为最终“拒答准确率”，因为最终模型还可能继续生成回答。
- **检索延迟**：统计检索耗时，用于衡量性能，不代表答案质量。
- **RRF**：是一种融合 Dense 与 BM25 排名的算法，负责“怎么排”，不是评价指标；MRR 才负责评价“排得好不好”。
- **Dense、Hybrid**：是被比较的检索方案，不是指标。
- **tuning、holdout**：是评测数据的用途划分，不是指标。tuning 用于调参，holdout 用于方案确定后的独立验证，避免在反复调参过程中对评测集过拟合。

#### 5. 最短记忆口诀

> Recall 看找没找到，MRR 看排得靠不靠前；上下文相关性看资料对不对题，忠实度看答案有没有依据，答案相关性看有没有真正回答问题。

### 追问：项目是否区分 tuning 与 holdout，BM25、Dense 和混合检索如何工作

#### 1. tuning 与 holdout 的真实实现

项目已经在评测数据中固定区分 `tuning` 和 `holdout`，`scripts/eval_retrieval.py` 与 `scripts/eval_rag.py` 都支持按 `all`、`tuning` 或 `holdout` 单独筛选样例。当前共 80 条评测样例：

- tuning 55 条，其中可回答 42 条、不可回答 13 条；
- holdout 25 条，其中可回答 18 条、不可回答 7 条。

这里没有训练或微调检索模型，所以不应把它们讲成机器学习意义上的训练集和测试集。准确说法是：tuning 是调优集，用于观察问题、调整分块、召回参数和 Prompt；holdout 是留出集，在方案确定后再运行，用来检查调整是否能泛化到未参与调优的样例。若反复查看 holdout 并据此继续修改方案，它也会逐渐变成事实上的 tuning，此时应该建立新的留出集。

#### 2. BM25：按词面证据查找

BM25 可以理解为“带权重的关键词检索”。项目先把知识子块与用户问题转成词项：中文通过 jieba 分词，同时额外保留英文、缩写、数字和单位等精确表达。随后按以下因素为每个知识块计算分数：

1. 查询词是否出现在知识块中，以及出现多少次；
2. 一个词在整个知识库中是否稀有，越少见通常区分度越高；
3. 对重复出现次数做饱和处理，避免单个词机械堆叠获得过高分；
4. 对文档长度做归一化，避免长知识块只因包含词更多而天然占优。

项目还使用正值 IDF 公式，减少小语料下常见词出现负 IDF 的问题。BM25 擅长命中动作名、专业缩写、数字和单位，例如“RPE 8”“肌酸 3—5g”；但对“意思相近、用词不同”的语义改写不够敏感。检索时只保留 BM25 分数大于 0 的候选，最多取 20 条，因此它并不保证每次硬凑满 20 条。

#### 3. Dense：按语义相似度查找

Dense 检索先使用本地 Embedding 模型把知识子块编码成稠密向量，并将正文、来源、父子关系和向量持久化到 SQLite。用户提问时，同一个 Embedding 模型把问题编码为查询向量；知识向量和查询向量都经过 L2 归一化，再由 FAISS 的 `IndexFlatIP` 计算内积。归一化后的内积等价于余弦相似度，因此分数越高，代表语义越接近。

Dense 擅长处理不同措辞表达同一含义的情况，例如“蛋白粉什么时候喝”和“蛋白质补充时机”；但对稀有缩写、精确数字和专有名词可能不如 BM25 稳定。SQLite 负责可靠保存知识、向量和元数据，FAISS 负责执行向量相似度搜索；二者不是两种召回路线。

#### 4. 当前混合检索的完整实现

当前默认检索策略是 Hybrid，完整过程如下：

1. 用户问题同时进入 Dense 和 BM25 两条召回路线；
2. Dense 召回语义最接近的 20 个子块，混合检索中不再使用固定相似度阈值做硬过滤；
3. BM25 召回词面得分大于 0 的候选，最多 20 个子块；
4. 两路分数不在同一尺度上，因此不直接相加，而是使用 RRF 按排名融合；
5. 某个候选在每条路线中的贡献为 `1 / (60 + rank)`，同时被两路命中的候选会累加两份贡献；
6. 按 RRF 总分排序后，再将命中的子块映射回父块，并折叠同一父块的重复结果；
7. 最终取 Top-5 父级上下文交给生成模型。

例如，一个子块在 Dense 排第 2、BM25 排第 3，RRF 分数约为 `1/62 + 1/63 = 0.0320`；另一个子块只在 Dense 排第 1，分数约为 `1/61 = 0.0164`。因此前者因为获得两路共识，通常会排在后者之前。

RRF 的价值是只比较名次，不必强行比较余弦相似度与 BM25 原始分数。它负责融合与排序，不是评测指标，也不等于语义过滤；最后取 Top-5 只是截断候选列表。与线性加权相比，RRF 少了分数归一化和权重调参；与 Cross-Encoder 重排相比，它的效果上限可能较低，但本地运行成本和延迟更可控，符合当前轻量原型的取舍。

#### 面试口述版

项目把评测数据固定分成 tuning 和 holdout：tuning 用于调整分块、召回和 Prompt，holdout 在方案确定后验证泛化，但它们不是模型训练集。检索时，BM25 根据关键词、词频、词的稀有程度和文档长度打分，擅长精确术语与数字；Dense 使用 Embedding 把问题和知识块转成归一化向量，再由 FAISS 按余弦相似度召回，擅长语义改写。两路各取最多 20 个子块，因为原始分数尺度不同，所以用 RRF 按名次融合，再做父块恢复和同父去重，最终取 Top-5 上下文交给模型。

#### 最容易混淆的层级

- BM25、Dense：两种召回方式；
- RRF：融合两路排名的算法；
- SQLite：知识、向量和元数据的持久化；
- FAISS：Dense 路线中的向量索引与相似度搜索；
- Recall@5、MRR：检索效果指标；
- RAGAS：包含多项生成与上下文指标的评测框架；
- tuning、holdout：评测数据的用途划分。

我把项目记忆概括为会话连续性和跨会话用户事实两条主线，但在实际注入 Prompt 时会进一步分层。每轮用户和助手消息都会完整写入 SQLite，最近六轮对话保留原文，保证代词、追问和任务状态能够连续理解。六轮之前的消息只是进入摘要候选区，只有候选内容达到字符数或估算 Token 水位才触发结构化摘要；摘要以 JSON 保存 `signals` 和可追溯的 `evidence`，并通过 `last_compacted_message_id` 只处理新增的旧消息。完整原文不会被删除，所以压缩的是 Prompt 视图，而不是底层历史记录。

### 第 6 题追问：敏感信息与置信度

#### 用户追问

> 哪些信息会被判断为敏感信息？怎么处理这种敏感信息？如果用户明确要求记住敏感信息怎么处理？同时这里的置信度是怎么计算的？

#### 当前代码的准确口径

1. 项目内部不是简单分成“敏感”和“不敏感”，而是有三档风险：低风险 `low`、健康敏感 `sensitive`和秘密 `secret`。当前分类是保守的关键词规则，不是语义模型。
2. 健康敏感词目前包括膝盖、腰、肩、旧伤、受伤、疼痛、疾病、高血压、糖尿病、过敏、手术和康复等。密码、口令、验证码、Token、API Key、身份证和银行卡等则归为秘密信息。
3. 健康敏感信息不能自动晋升，也不会作为未确认的软记忆注入 Prompt，而是进入 `review_required` 观察项或 `pending` 候选，等待用户确认或拒绝。秘密信息则直接被记忆写入链路拒绝，无论用户是否说“请记住”都不会成为候选或长期记忆。
4. 例如“请记住我膝盖有旧伤”会先进入待确认候选；用户确认后才转成可检索的长期记忆，拒绝后不参与后续回答。“请记住我的 API Key”则直接被记忆子系统跳过。
5. 需要主动交代一个实现边界：“秘密不写入记忆子系统”不等于“原始消息绝对不落库”。当前完整会话会写入 SQLite，而记忆防护链路未对原始消息做脱敏或加密。因此不能在面试中包装成生产级隐私保护；生产化还需要输入脱敏、静态加密、权限隔离、保留期限和删除机制。
6. `0.68→0.82→0.95` 这套置信度只针对隐式观察候选，不是大模型返回的概率，也不是 Embedding 相似度。新的独立证据写入后，按 `confidence = min(0.95, 0.68 + 0.14 × (evidence_count - 1))` 计算：一条证据为 `0.68`，两条为 `0.82`，三条起封顶为 `0.95`。
7. 证据会按消息来源去重。自动晋升不只看置信度，还必须同时满足低风险、无冲突、至少两条证据和来自至少两个会话。因此同一会话里反复表达即使使置信度升高，`conversation_count` 仍不达标，不会自动晋升。健康敏感候选即使置信度达到 `0.95`，也仍被风险门禁拦住，只能由用户确认。
8. 显式记忆不走这套证据累积公式。低风险显式指令可直接写入；显式敏感候选由用户人工确认后，以用户确认事实处理，长期记忆置信度为 `1.0`。
9. `0.68`、`0.14`、`0.82` 是为了实现“一次低风险信号可作软线索，两次跨会话证据才能晋升”所设的可配置工程默认值，并未经过统计校准，不能宣称是真实准确率。如果生产化，应用误记率、候选接受率和用户撤销率调参。

### 第 6 题追问：为什么健康信息需要隔离

#### 用户追问

> 为什么健康敏感词要隔离，不应该更好地了解后才能给用户制定合适的计划吗？

#### 正确口径

这里的“隔离”不是让 Agent 忽略健康信息，而是隔离**未经确认的健康信息被自动固化和跨会话使用**。用户在当前对话中提到膝盖疼、过敏或旧伤时，这些内容仍存在于当前问题和近期对话中，Agent 可以立即据此给出更保守的建议；系统只是不会把一次表达自动当成永久事实，也不会把它作为未确认软记忆在以后无关的会话中反复注入。

健康信息比普通偏好具有更高的误记成本。一句“今天膝盖疼”可能是临时状态，“我朋友膝盖有伤”也不代表用户本人有伤；如果系统误存为长期事实，后续训练计划会持续受到错误约束。同时，伤病和疾病信息本身具有更高的隐私风险，因此需要用户确认其主体、持续性以及是否允许跨会话保存。

确认后的健康信息并不会继续被排斥。它会成为可召回的长期记忆，并在训练或饮食任务中作为重要安全约束参与 Prompt 组装。理想流程是：当前轮立即谨慎使用，提示用户确认是否长期保存；确认后跨会话优先使用，拒绝后只保留本轮语境。核心原则是“当前使用可以及时，长期固化必须审慎”。

当前原型仍有边界：敏感识别采用关键词规则，不能准确区分临时症状、他人信息和确诊病史；确认交互也仍可进一步优化为带原文、用途和有效期的明确授权。面试时不应把它包装成完整的医疗隐私系统。

#### 一句话记忆

> 隔离的不是健康信息本身，而是未经确认的健康信息被自动长期保存和跨会话使用；确认后，它反而应作为高优先级安全约束参与计划生成。

### 第 6 题追问：待确认与隔离是否重复

#### 用户追问

> 那不就还是通过待确认的步骤去确认就可以了，没必要隔离。

#### 正确口径

这个判断基本正确，不需要在“待确认”之外再建立一套独立的用户流程。“待确认”描述候选信息的状态，“隔离”描述该状态对应的使用权限：候选可以保存在数据库中并展示给用户确认，但确认前不能自动晋升，也不能作为跨会话软记忆注入 Prompt。当前轮仍可依据用户原话谨慎回答。

因此更准确的表达不是“先隔离、再确认”两个步骤，而是“健康信息进入待确认状态，并在确认前限制其跨会话使用”。如果待确认信息仍能和正式记忆一样参与后续生成，那么待确认就只剩一个标签，无法真正降低误记风险。

#### 一句话记忆

> 待确认是数据状态，隔离是该状态的权限规则；对用户只有一次确认流程，不是两套流程。

### 第 6 题完成状态

### 面试官评阅

#### 回答正确的部分

- 抓住了模型上下文上限、输出预留、安全余量和输入预算之间的关系。
- 正确区分了两类动作：持久化会话摘要主要处理较早对话，Prompt 裁剪则面向本轮即将发送给模型的完整输入。
- 正确意识到系统规则和当前问题不能像普通上下文一样被随意舍弃，RAG 证据和已确认长期记忆属于高价值内容。
- 正确说明摘要链路异常不能阻塞用户的当前请求，系统需要保留最近对话作为保底上下文。

#### 需要修正和补充的部分

1. 不能说“模型一般只有一个 `config.json` 字段”。项目会依次检查 `config.json`、`tokenizer_config.json` 和运行时模型配置，并兼容 `max_position_embeddings`、`n_positions`、`model_max_length` 等多个字段；如果都取不到才使用默认 `4096`。环境配置只能把已声明的窗口进一步收紧，不能把模型真实上限扩大。
2. `模型上下文上限 - 输出预留 - 安全余量` 得到的是**最大 Prompt 预算**，不是压缩触发阈值。项目默认在该 Prompt 预算的 `80%` 左右提前触发本轮 Prompt compact，最后再由真实 tokenizer 做硬 Token 校验。
3. 持久化会话摘要仍有独立的触发阶段：先保留最近六轮原文，再检查六轮之前尚未摘要的候选。摘要水位默认由模型窗口推导出的 Prompt compact Token 线按 35% 派生，并限制在 `900—4000` Token；字符线按 4 倍同步派生。它与本轮 Prompt compact 不是同一次操作。
4. “裁剪除了安全规则和问题外的所有内容”过于绝对。系统角色、全局规则、安全约束、当前问题和已确认的伤病、过敏、禁忌等安全记忆会被固定保留；其他内容才进入可选候选队列。
5. 裁剪不是按“先装完 RAG，再装长期记忆，最后装摘要”的严格顺序，也不是到了末尾再从低到高删除。核心候选按优先级建立队列，然后采用轮转装箱：RAG 证据、确认记忆、运行时结构化状态、近期对话和历史摘要每轮各尝试加入一个完整语义单元；某条放不下就跳过，继续尝试其他队列，避免 RAG 一次占满全部预算。普通信息和软记忆最后利用剩余空间。
6. 每个候选按完整语义单元保留或舍弃，不会从一条 RAG 片段、一轮对话或一条记忆的中间生硬截断；最后仍执行硬 Token 上限校验。
7. “摘要生成失败后进行滑动窗口压缩”不准确。当前持久化摘要是确定性的结构化整理，不依赖大模型重新生成。摘要读取、解析或更新异常时，系统记录降级原因，保留已经写入 SQLite 的完整原始消息，并退回最近六轮原文继续回答；这是**滑动窗口保底**，不是再次执行一种压缩。
8. 如果连固定规则、当前问题和安全记忆本身都超过硬预算，系统不会悄悄删除这些关键约束，而会由硬校验暴露预算不足。这是原型的明确边界，不能包装成任何长度都能自动处理。

### 第 7 题参考答案

我会先把“持久化会话摘要”和“本轮 Prompt compact”分开说明。系统优先从模型的 `config.json`、`tokenizer_config.json` 或运行时配置读取上下文窗口，并兼容多个常见字段；无法识别时才回退到 `4096`。设窗口为 `C`、模型回答预留为 `G`、安全余量为 `S`，则最大 Prompt 预算是 `P=C-G-S`，项目默认在 `P` 的约 `80%` 提前触发 compact，最终发送前再由模型 tokenizer 精确计数并做硬上限校验。

会话摘要负责压缩较早的对话视图。系统始终保留最近六轮原文，六轮之前尚未处理的消息达到动态字符线或估算 Token 水位时，才按上次压缩边界增量整理成带 `signals` 和 `evidence` 的结构化摘要；原始消息仍完整保存在 SQLite 中。摘要触发和本轮 Prompt 裁剪是两套机制，但默认摘要水位会从稳定的 Prompt compact 预算派生，避免继续使用与模型容量无关的固定经验值。

本轮完整 Prompt 超过主动阈值时，系统固定保留角色规则、安全约束、当前问题以及已确认的伤病、过敏和禁忌等安全记忆。RAG 证据、普通确认记忆、运行时结构化状态、近期对话和历史摘要等内容被拆成完整语义单元并进入不同优先级队列。核心队列采用轮转装箱，每轮各尝试加入一条；某条放不下就跳过并继续检查其他队列，避免最高优先级的 RAG 独占全部空间。低优先级普通信息和软记忆最后填充剩余预算，最后执行硬 Token 校验。

如果会话摘要读取或更新异常，已经落库的原始对话不会丢失，系统会记录降级并退回最近六轮原文继续回答，不让摘要链路阻塞主流程。这里是滑动窗口保底，不是再生成一份压缩摘要。若固定内容本身已经突破模型硬上限，则由硬校验明确报出预算不足，而不是静默删除安全规则或当前问题。

### 第 7 题追问：最大 Prompt 预算与会话摘要阈值

#### 用户追问

> 所以最大 Prompt 预算是裁剪的阈值，而压缩的阈值是固定的 3000 字符？这个阈值会不会有点低了？

#### 正确口径

最大 Prompt 预算不是裁剪的触发阈值，而是本轮输入绝对不能突破的硬上限。设模型窗口为 `C`、回答预留为 `G`、安全余量为 `S`，则最大 Prompt 预算为 `P=C-G-S`；项目默认在 `T=0.8P` 左右主动触发 Prompt compact，给估算误差和后续内容留出空间，最终再由 tokenizer 做硬上限校验。因此这里存在“主动裁剪线 `T`”和“硬上限 `P`”两道线。

会话摘要只统计最近六轮之外、尚未摘要的旧消息。默认 Token 水位是 `clamp(floor(T×0.35), 900, 4000)`，其中 `T` 是本轮 Prompt 的主动 compact Token 线；字符水位默认取该结果的 4 倍，任一条件达到就触发。以 8192 Token 模型、1024 Token 输出预留和 256 Token 安全余量为例，`T=5529`，摘要水位为 `1935` Token、`7740` 字符。显式环境变量仍可覆盖自动值。

当未知模型回退到 `4096` Token 上下文时，最大 Prompt 预算约为 `2816` Token、主动 compact 线约为 `2252` Token，按公式计算会命中 `900` Token 下限。这是小上下文模型的保护下限，不是所有模型共用的固定阈值。最近六轮原文仍保留，完整消息也仍在 SQLite，因此提前摘要不等于删除历史。

对于 `32K`、`128K` 等长上下文模型，摘要水位会随主动 compact 线提高，但最多限制在 `4000` Token，避免一次处理过多旧消息。当前实现属于“按模型预算派生、在服务启动后保持稳定”的工程水位，不应包装成经过大规模长对话评测得到的最优比例；`35%` 和上下限仍需用信息保留率、Token 占用与回答连续性继续校准。

#### 一句话记忆

> 最大 Prompt 预算是应用输入硬上限，约 80% 是本轮 Prompt 的主动 compact 线；旧对话摘要只处理最近六轮以外的内容，触发水位默认按这条 compact Token 线的 35% 动态派生，并限制在 900—4000 Token。

### 第 7 题追问：摘要阈值能否随模型预算动态调整

#### 用户追问

> 那是不是也可以根据模型的上下文预算来调整这个压缩阈值？

#### 正确口径

可以，而且当前已经采用这种方式：先根据模型上下文窗口得到最大 Prompt 预算和主动 compact 线，再给旧对话分配其中一部分预算。当前公式是：

```text
旧对话摘要阈值 = clamp(主动 compact Token 线 × 35%, 900, 4000)
```

其中 `35%` 表示只允许未摘要旧对话占用约三分之一的安全输入空间，剩余预算留给系统规则、当前问题、最近六轮、RAG 和长期记忆；`900` 是小上下文模型的下限，避免频繁生成过小摘要；`4000` 是上限，避免长上下文模型积累过多旧消息后一次性处理。这个比例和上下限都是需要评测校准的工程策略，不是行业标准。

字符阈值也必须跟着 Token 阈值同步调整，否则旧版 `3000` 字符配置仍可能提前触发，使动态 Token 阈值失效。当前默认按 Token 水位的 4 倍同步派生字符水位，实际判断保留“字符或估算 Token 任一越线即触发”，最终 Token 安全由 tokenizer 和本轮 Prompt 硬校验负责。

需要注意模型切换：同一会话可能从长上下文 DeepSeek 切到较小的本地模型，如果持久化摘要水位每轮随当前模型大幅变化，会出现策略抖动。当前实现因此在服务启动时按项目解析出的稳定 Prompt compact 预算派生一次摘要水位，不随单次请求选择的模型来回变化；显式 `CONVERSATION_SUMMARY_TRIGGER_TOKENS/CHARS` 仍可覆盖。更完整的方案可以按模型保存摘要版本，并允许根据 SQLite 原始消息重新构建不同粒度的摘要。

#### 一句话记忆

> 摘要阈值已由模型派生的主动 compact 预算按比例计算并设置上下限，字符阈值同步派生；当前采用启动时稳定配置，避免每次模型选择造成水位抖动，但还没有做到按模型维护多个摘要版本。
