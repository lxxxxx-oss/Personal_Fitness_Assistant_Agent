# 混合意图路由专项面试问答

> 对应简历亮点：基于 LangGraph 组织多类业务子图，以加权规则、组合模式和置信度区分单意图、可靠复合意图与候选竞争；歧义时定向澄清并跨轮恢复，可靠多意图按用户表达顺序执行，并用常规集、困难集和语义改写集持续回归。
>
> 使用原则：先背“30 秒回答”和“完整链路”，再理解术语与追问。回答时必须区分当前实现、实验能力和生产化方向。

## 1. 30 秒可直接回答

> 这个项目不是让大模型自由决定所有流程，而是用 LangGraph 把 Chat、Search、Diet、Motion、MCP 五类能力组织成受控工作流。Router 通过加权规则、组合模式、否定词和置信度判断主意图、次意图与执行顺序。显式的“先做 A 再做 B”属于可靠多意图；若两个候选都成立但缺少可验证的复合结构，则先点名两个候选让用户澄清，本轮不调用业务子图。系统按会话保存待决任务，下一轮能根据“第一个”“饮食建议”或“两个都要”恢复单路或多路执行。这样既避免把歧义误当多意图，也保留了可解释、可测试和可恢复的路由链路。

## 2. 90 秒项目展开

> 用户请求进入系统后，Router 会对五个注册意图计算分数。分数不只是关键词计数，还包含组合模式、文件信号、时效词、否定约束和边界冲突。例如“最新研究”提升 Search，“番茄炒蛋怎么做”进入 MCP 菜谱工具，“不需要具体做法”会抑制 MCP。Router 根据最高分、次高分和分差计算置信度；明确的“先、再、然后”决定执行顺序，“同时、顺便”只有在两个分句都能可靠识别时才形成多意图。若至少两个候选超过门槛、得分接近，但原句没有可靠的顺序或并列结构，系统不会擅自执行两项，而是生成只包含前两名候选的定向澄清问题。
>
> 澄清轮会在业务执行前结束，不调用子图、工具或生成模型；系统保存原始请求、两个候选、分数和澄清问题。普通会话的待决状态按用户与会话写入 SQLite，服务重启后仍能恢复；临时会话只保存在内存。下一轮支持序号、能力别名、自然序数和“两个都要”，解析成功后把原始请求与澄清答案组合起来重新路由；仍不明确就继续澄清，取消或转入明确新请求则清理状态。它是短暂的任务状态，不是长期记忆，也不会注入普通 Prompt。
>
> 正常执行时，输出不再只是一个 intent，而是 `primary_intent`、`secondary_intents` 和 `route_plan`。计划执行前统一做合法性、去重和最多三步校验，不检查固定组合白名单。之后顺序执行所有合法子图，步骤之间共享结构化状态；某一步失败会留下 warning 并继续后续步骤，全部失败才返回整体错误。多步执行结束后只做一次 final synthesis，单步请求不额外增加合成调用。
>
> 我用三组数据回归：常规集 66/66；challenge set 主意图 36/36、次意图精确匹配 34/36、route plan 36/36；语义改写集 10/10。这些是当前离线数据上的结果，不代表线上自然语言永远达到同样准确率。

## 3. 第一次出现的技术点

### 3.1 Agent、Workflow 与 Planner

- **是什么**：Agent 通常指能够根据目标使用模型、记忆和工具完成任务的系统；Workflow 是代码预先规定主要执行路径的流程；Planner 是把目标拆成步骤并决定执行关系的组件。
- **解决什么问题**：纯 LLM 只能生成文本，Agent/Workflow 把生成能力接到检索、数据库、动作分析和外部工具上；Planner 负责多步骤任务。
- **项目中怎么用**：项目属于“受控 Agent Workflow”。Router 只能从五个已注册子图中生成最多三步的顺序计划，不会发明新工具、循环或任意依赖。
- **类似方案**：纯关键词 if/else、LLM Function Calling、ReAct 循环、开放式 Planner、多 Agent 编排。
- **为什么这样选**：健身建议涉及健康边界，确定性路径更容易测试、观测和降级；当前业务只有五类明确能力，没有必要承担开放 Planner 的成本和不可控性。

### 3.2 LangGraph 与 StateGraph

- **是什么**：LangGraph 是面向有状态工作流/Agent 的图编排框架；StateGraph 用共享 State 表达节点输入输出，用边描述执行顺序和条件分支。
- **解决什么问题**：当流程包含路由、分支、多步骤执行、状态共享、失败处理时，线性 Chain 会变得难以维护。
- **项目中怎么用**：顶层图先执行 Router，再进入 Chat、Search、Diet、Motion 或 MCP 子图；多意图时按 `route_plan` 顺序调用子图，结果写回统一状态，最后合成。
- **类似方案**：LangChain Runnable/Chain、LlamaIndex Workflow、Temporal、Airflow、自研状态机。
- **为什么这样选**：它能清楚表达“路由—子图—合成”，又允许节点内部保留普通 Python 确定性逻辑；比上重型工作流引擎更适合本地原型。

### 3.3 意图识别、主意图、多意图与歧义

- **是什么**：意图识别把用户表达映射到业务能力；主意图是本轮优先任务，次意图是同一句中还需执行的任务，多意图表示用户明确要求完成多个目标。歧义则表示多个解释都说得通，但系统无法确认用户究竟想选一个还是多个。
- **解决什么问题**：只返回一个标签会丢失“先分析动作，再给饮食建议”中的第二个任务；把所有高分候选都当成多意图，又会在模糊表达下错误调用多个能力。
- **项目中怎么用**：可靠顺序词或并列分句形成 `route_plan`；候选接近但缺少可靠复合结构时设置 `_needs_clarification`，并保留前两名候选。内部状态还保存 `_primary_intent`、`_secondary_intents` 和 `_multi_intent_reason`。
- **类似方案**：单标签分类、多标签分类、序列标注、LLM 结构化分类、规划器拆解。
- **为什么这样选**：业务类别少但复合表达真实存在，显式 route plan 比仅做多标签更能指导执行。

### 3.4 加权规则与组合模式

- **是什么**：加权规则为不同信号分配不同分数；组合模式要求多个词或结构共同出现才加分。
- **解决什么问题**：单关键词容易误判，例如“最近想瘦”不一定要搜索最新资料，“苹果”可能是食物也可能出现在其他语境。
- **项目中怎么用**：时效词、上传文件、菜名/做法、饮食规划、动作分析等信号分别加权；“最近+研究”比单独“最近”更强；否定词可以抑制某条路线。
- **类似方案**：决策树、朴素贝叶斯、传统分类器、embedding 相似度、LLM 分类。
- **为什么这样选**：规则量可控、解释清楚、无需模型推理延迟，并能把安全边界显式编码。

### 3.5 置信度、分差与定向澄清

- **是什么**：置信度表示系统对分类结论的把握；分差是最高分与次高分的差；定向澄清是在两个有效候选难以取舍时，只围绕这两个候选向用户确认。
- **解决什么问题**：最高分不等于可靠。两个意图得分接近时，强行执行可能答非所问或错误调用工具。
- **项目中怎么用**：综合最高分、是否超过最低分和与第二名分差形成置信度。没有有效业务候选时才走普通 Chat；至少两个候选过门槛、得分接近且缺少可靠复合结构时走定向澄清，不凭空扩展多意图。
- **类似方案**：softmax 概率、熵、校准曲线、拒识分类、人工确认。
- **为什么这样选**：规则分数不是严格概率，项目把置信度当工程决策信号而非统计意义上的真实概率。

### 3.6 待决任务状态与跨轮恢复

- **是什么**：待决任务状态是一次未完成路由的短暂快照；跨轮恢复是下一轮利用该快照继续完成原任务。
- **解决什么问题**：如果只返回澄清问题却不保存原请求，用户回答“第二个”时系统不知道“第二个”指什么；服务重启还可能丢失上下文。
- **项目中怎么用**：保存原始输入、前两名候选、分数和澄清问题；普通会话按 `user_id + conversation_id` 持久化到 SQLite，临时会话仅存内存。解析成功、取消或明确转入新请求后清除状态。
- **类似方案**：只依赖最近对话让 LLM猜测、把待办写入长期记忆、前端携带隐藏字段、服务端有限状态机。
- **为什么这样选**：服务端显式状态可以校验、测试并在重启后恢复；它只服务当前任务，不污染长期画像，也不需要把整段历史重新塞进 Prompt。

### 3.7 回归集、Challenge Set 与语义改写集

- **是什么**：回归集用于检查修改后旧能力是否退化；Challenge Set 专门放边界、歧义和易错样例；语义改写集用同义表达测试泛化。
- **解决什么问题**：Router 很容易“修一个 case、坏另一个 case”，只凭手测无法发现系统性回退。
- **项目中怎么用**：分别评测公开 intent、主/次意图和 route plan，不只看一个标签。
- **类似方案**：线上 A/B、人工红队、属性测试、模糊测试、真实流量回放。
- **为什么这样选**：个人项目没有大规模线上流量，分层离线集能以较低成本形成可复现证据。

## 4. 当前完整链路

```text
用户文本/文件信号
  -> 文本归一化与规则特征提取
  -> 五类意图分别累计分数
  -> 组合模式、否定词和边界规则修正
  -> 计算最高分、次高分、分差与置信度
  -> 没有有效业务候选：进入普通 Chat
  -> 单个可靠候选：生成单步 route_plan
  -> 有显式顺序/可靠并列结构：生成多步 route_plan
  -> 两个候选接近但无法确定：
       -> 返回只点名前两名候选的澄清问题
       -> 本轮不调用业务子图、工具或生成模型
       -> 普通会话写入 SQLite 待决任务状态；临时会话写入内存
       -> 下一轮解析序号、能力别名、自然表达或“两个都要”
       -> 解析成功：结合原始请求恢复单路或多路路由
       -> 仍不明确：继续澄清；取消/明确新请求：清理状态
  -> 校验合法意图、去重、最多三步
  -> 按用户表达顺序执行子图
  -> 每步结果/错误写入统一 State
  -> 多步 final synthesis；单步直接返回
  -> 输出回答、intent、execution trace、warnings
```

五条子图是：

| 子图 | 主要职责 | 典型输入 |
|---|---|---|
| Chat | 健身知识问答，结合 RAG | “增肌为什么要渐进超负荷？” |
| Search | 需要最新外部信息的查询 | “搜索最近的力量训练研究” |
| Diet | 摄入量、营养和饮食规划 | “减脂期晚餐怎么安排？” |
| Motion | 动作指导或姿态数据分析 | “先分析这段深蹲动作” |
| MCP | 外部菜谱工具 | “番茄炒蛋怎么做？” |

## 5. 高频面试问题与完整回答

### Q1：为什么不直接让 LLM 做路由？

> 我做过这个方向的实验，但没有默认启用。当前业务只有五个稳定意图，大部分边界可以由强信号和组合模式清楚表达。确定性 Router 延迟低、可解释、能做精确回归，也不会因为模型版本或温度变化而漂移。本地 Qwen A/B 在现有 challenge set 上没有提升整体准确率，还带来秒级延迟和误覆盖高置信规则的风险，所以我把它保留为 feature flag，而不是为了显得“更智能”强行放进主链路。生产中如果自然语言分布扩大，我会先积累未覆盖样本，再比较规则、轻量分类器和 LLM 的增量收益。

### Q2：为什么叫“混合意图路由”？混合在哪里？

> “混合”不是指线上每次同时调用规则、embedding 和 LLM。主链路混合了关键词权重、组合模式、文件/工具信号、否定约束、置信度和多意图顺序识别；代码还保留 embedding 样例匹配和本地 Qwen 分类器作为可选实验层，但默认关闭。面试时我会明确说“当前默认是确定性混合信号路由”，避免让人误以为三套模型都在线执行。

### Q3：加权规则是不是大量 if/else，很难维护？

> 如果把规则散落在业务节点里，确实会失控。项目把意图集合、词项权重、组合模式、阈值和输出协议集中在 Router 模块，路由只负责决策，不执行业务。每次新增规则必须补常规、困难或改写样例，观察主意图、次意图和计划是否回退。规则仍有上限：当类别和语言分布继续扩大时，应把稳定规则保留为安全护栏，把长尾识别迁移到经过校准的分类器，而不是无限堆叠。

### Q4：置信度是如何计算的？它是真实概率吗？

> 它由最高规则分、是否超过最低路由分数，以及最高分和第二名的 margin 综合得到，用来控制单意图、多意图和澄清。当前在至少两个候选过最低分、又没有顺序或并列结构时，以 `0.80` 作为工程决策阈值：低于它先澄清，达到它则选择占优的单意图。它不是训练出来的 calibrated probability，因此不能解释为“80% 的真实正确概率”。生产化会用带标注的真实流量做 reliability diagram、ECE 或按区间统计准确率，再校准阈值；面试时要说明 `0.80` 是当前回归下的工程取值，不是行业标准。

### Q5：怎样判断一句话是真的多意图，而不是关键词碰撞？

> 我同时检查三个条件：第一，每个候选意图都要有足够独立证据；第二，显式顺序词或并列词要和分句结构一致；第三，不能被否定约束推翻。“先分析深蹲，再给饮食建议”有两个清晰任务和顺序；“我最近想减脂”只有“最近”这个弱时效词，不会因此扩展 Search。只有一个可靠候选就走单意图；多个候选接近却没有可靠复合结构，则进入澄清，不会自动扩展成多意图。

### Q6：两个意图都过了第一层、分数又接近，为什么不直接当成多意图？

> “系统看见两个可能”不等于“用户要求完成两个任务”。多意图需要语义上的组合证据，例如两个独立分句以及“先、再、同时、顺便”等可靠连接；得分接近只说明分类器难以取舍。如果仅凭两个高分就执行两条链路，系统可能多调工具、增加延迟，甚至给出用户没要的建议。因此当前把“候选竞争”和“明确复合任务”分开：前者澄清，后者才生成多步计划。

### Q7：定向澄清问题是怎么生成的，为什么不用 LLM？

> Router 取前两名有效候选，映射成用户能理解的能力名称，生成“你更想做 A、B，还是两项都做”这类受控问题。当前只有五类能力，模板生成更稳定、延迟更低，也不会让模型发明不存在的选项。LLM 澄清适合候选空间大、需要复述复杂上下文的场景；本项目先用确定性模板覆盖主链路，后续若扩展能力再用受约束的结构化生成，而不是现在为了技术名词增加一次模型调用。

### Q8：用户只回答“第二个”，系统怎样恢复原来的路由？

> 澄清时服务端会保存原始输入、前两名候选、分数和问题，并以用户与会话作为作用域。下一轮先检查是否存在待决状态，再解析“第一个/第二个、前者/后者、先做第二个、饮食建议、两个都要”等表达。解析到一个候选，就把原始请求和选择组合后恢复单路；解析到“两项都要”，就恢复受约束的多路计划；仍不清楚则再次澄清。普通会话的状态写入 SQLite，所以后端重启后仍能继续；临时会话只保证进程内有效。

### Q9：待决澄清状态为什么不放进长期记忆？何时清除？

> 它描述的是“这一次任务还没选完”，不是用户稳定偏好或个人事实。如果写进长期记忆并持续注入 Prompt，后续无关请求可能被旧任务干扰。当前把它作为独立任务状态：解析成功后清除，用户取消时清除，用户转入一个已经足够明确的新请求时也清除；只有答案仍像对原问题的含糊补充时才继续保留并再次澄清。

### Q10：为什么取消固定组合白名单？风险怎么控制？

> 白名单在组合少时简单，但五个意图两两、三三组合很快膨胀，而且容易拒绝合理新表达。取消后并不是无限开放，而是把控制从“组合级枚举”改成“步骤级约束”：只允许已注册意图、去重、最多三步、保持用户顺序，并对每步做失败隔离。这样可扩展性更好，同时执行范围仍然可计算、可测试。

### Q11：为什么最多三步？

> 三步是当前原型的资源和复杂度预算，不是行业标准。它限制一次请求的模型调用、工具调用和状态膨胀，也避免错误拆解造成长链路放大。超出部分会截断并写 warning。生产中应根据 P95 延迟、工具成本、任务完成率和真实多步骤分布调参；如果经常出现复杂依赖，就不该简单提高上限，而应引入显式 Planner、依赖图和确认机制。

### Q12：多意图为什么顺序执行，不并行？

> 当前复合任务经常有隐含依赖，例如“先搜索食材，再基于结果推荐饮食”，顺序执行能让后一步读取前一步的结构化状态，也更容易保证输出顺序和错误语义。并行适合相互独立、只在末尾聚合的任务，但需要定义并发写 State 的合并规则、超时和取消策略。当前最多三步，顺序执行的可解释性收益大于吞吐收益。

### Q13：LangGraph 在这里具体解决了什么，自研状态机不行吗？

> 自研完全可以，尤其当前图并不巨大。LangGraph 的价值是把共享 State、条件分支、子图和执行轨迹统一成成熟抽象，后续接持久化、流式输出或人工确认时也有演进空间。代价是引入框架概念和版本依赖。因此项目没有把每个普通函数都包装成 Agent 节点，而是只在跨模块编排处使用图，节点内部仍用普通 Python。

### Q14：State 里存什么？为什么不把所有结果都拼成字符串？

> State 同时保存用户输入、路由决策、route plan、结构化业务状态、工具摘要、错误和最终回答。结构化数据能让后续节点读取明确字段，避免从自然语言反解析，也方便测试和观测。大结果不会无上限写入 State，工具只保留裁剪后的 summary，完整事实仍由各自存储负责，否则多步请求会造成上下文和序列化成本膨胀。

### Q15：一步失败后为什么继续？会不会让后续结果失真？

> 是否继续取决于依赖关系。当前 Router 不建复杂依赖图，所以默认把各步骤当作可独立完成：单步异常被记录，后续步骤继续，最终明确说明部分失败。如果后一步明确需要前一步产物，则应在子图入口检查所需状态，缺失时返回“依赖未满足”而不是伪造结果。全部步骤失败时才升级为整体错误。

### Q16：最终合成怎样避免二次幻觉？

> 合成 Prompt 只接收各步骤的结构化摘要、来源和错误，不允许把失败步骤写成成功；要求保留事实边界和 warning。更严格的生产方案会让合成输出结构化字段，逐条关联 evidence ID，再由模板渲染，而不是完全依赖自由文本。目前项目完成了失败信息保留和一次性合成，但还没有 claim-level 引用校验。

### Q17：如何评测路由？为什么不能只看 Accuracy？

> 单意图可以看整体准确率，但多意图至少要分开看主意图、次意图集合和 route plan。主意图对但顺序错，执行仍可能错误；次意图漏掉也会造成任务不完整。因此当前评测分别比较 `primary_intent`、`secondary_intents` 和 `route_plan`，再按常规、challenge、语义改写切片看问题来源。线上还应补拒识率、澄清率、任务完成率、P95 延迟和错误工具调用率。

### Q18：当前结果好不好？可以说路由 100% 吗？

> 可以准确说：当前固定离线数据上，常规集 66/66、challenge 的主意图和计划 36/36、语义改写 10/10；但 challenge 次意图精确匹配是 34/36，也就是 94.4%。不能概括成“所有路由 100%”，更不能外推到生产流量。这个结果证明的是当前规则对已知边界可回归。

### Q19：embedding fallback 的原理和边界是什么？

> 它把用户句子和每类代表样例编码成向量，按余弦相似度选择最接近的意图，适合处理词面不同但语义接近的改写。缺点是容易受样例覆盖、embedding 模型和阈值影响，也可能把模糊请求强行吸到某一类。当前实现保留了这层能力但默认关闭，只有规则无法形成稳定结论时才有实验价值；启用前要在新增长尾集上证明收益并设置拒识阈值。

### Q20：本地 Qwen 分类器怎样避免覆盖正确规则？

> 原则是“模型只能在规则不确定时接管”，而不是无条件覆盖。需要结构化输出约束意图集合、置信度和理由，设置超时与 feature flag；高置信规则场景只有模型有更强证据时才考虑改变，并记录两者分歧。当前 A/B 没证明收益，所以默认不调用，这本身也是评测驱动选型的结论。

### Q21：Router 和 RAG Retriever 有什么区别？

> Router 决定“这个请求应该进入哪条业务链路”，输出意图和执行计划；Retriever 在 Chat/Diet 子图内部决定“从知识库拿哪些证据”，输出上下文。前者是上层业务编排，后者是知识检索。用户问最新研究时 Router 可能进入 Search；问稳定健身知识时进入 Chat，再由 Retriever 做 Dense+BM25 混合检索。

### Q22：这算多 Agent 吗？

> 更准确地说是一个 Agent 应用中的多子图工作流，而不是多个自治 Agent。五条路径有独立职责，但共享同一个顶层 Router 和 State，没有各自长期目标、独立规划循环或点对点通信。面试时不把“多个模块”夸大成“多 Agent 系统”，反而能体现架构边界意识。

### Q23：如果线上出现新意图，怎么演进？

> 先收集未命中、低置信和用户纠正样本，判断是现有意图的长尾表达还是确实需要新能力。若只是长尾，补组合规则、样例分类器或语义层，并回归所有数据；若是新业务，则先定义子图契约、输入输出、权限和失败语义，再注册新意图。不能只给 Router 加一个标签却没有真实执行路径。

### Q24：怎样防止 Prompt Injection 让 Router 调用不该用的工具？

> Router 只从注册意图集合选择，不把用户文本当系统指令执行；工具层还要独立做参数校验、权限控制和错误映射。路由正确不等于工具调用安全。高风险写操作需要确认或权限令牌，外部返回内容按不可信数据处理，不能因为文本写着“忽略规则”就改变系统策略。当前项目工具以读取和分析为主，生产化仍需鉴权、速率限制和审计。

## 6. 反问式压力题

### “这不就是规则系统，为什么叫 Agent？”

> Agent 的价值不等于所有决策都必须由 LLM 完成。这个项目由模型生成回答，能调用检索、搜索、菜谱和动作分析工具，并通过有状态图完成多步骤任务；Router 使用确定性策略是为了把高频业务边界变成可验证控制面。更准确的定位是“确定性 Workflow 约束下的 Agent”，而不是完全自治 Agent。

### “既然 Qwen 没用，为什么代码里还保留？”

> 因为它已经形成可开关、可观测的实验接口，便于未来用真实长尾数据重新 A/B；但主链路只启用经过证据证明的能力。保留实验接口和宣称它在线生效是两件事，我会明确区分。

### “三步串行会很慢，设计是不是有问题？”

> 它用可控延迟换取依赖清晰和状态一致。当前三步上限使最坏情况有界；执行轨迹可以定位耗时。若真实数据表明独立步骤占比高，我会在计划中显式标注依赖，把无依赖步骤用并行 fan-out 执行，再用 reducer 合并，而不是直接把所有步骤并发化。

### “离线集是不是你自己出的，所以分数没有意义？”

> 自建数据确实存在偏差，所以我不把它当生产泛化证明。它的价值是形成变更回归和边界清单。下一步应引入盲测标注、真实匿名请求、不同人改写和错误样本回灌，并把 tuning 与 holdout 分开。回答重点不是声称数据绝对好，而是说明我知道证据的适用范围。

### “定向澄清不就是写死的菜单吗？”

> 它确实是受控交互，但不是固定显示同一张菜单：系统会根据本轮得分动态选择前两名候选，并把用户选择恢复成真实路由。这里追求的不是让问题措辞无限变化，而是减少错误工具调用并保证答案可解析。候选只有五类时，确定性模板比再调用一次 LLM 更符合成本和稳定性目标；候选空间扩大后，才有必要引入结构化生成。

### “后端重启后用户回答‘第二个’，不会丢吗？”

> 普通会话不会只靠进程内变量，待决任务按用户和会话写入 SQLite，重启后会先恢复再解析答案；临时会话为了不落盘，只保证当前进程内有效。我会把这两种边界讲清楚，不宣称所有模式都具备持久化恢复。

## 7. 白板讲解顺序

1. 先画五个子图，说明 Router 是上层业务路由，不是 Retriever。
2. 写出 `primary + secondary + route_plan`，解释为何单标签不够。
3. 从“信号打分—置信度”分出三条边：单意图、可靠多意图、候选竞争。
4. 在候选竞争分支画“定向问题—保存待决状态—下一轮解析—恢复路由”，并标注澄清轮不执行子图。
5. 再画多意图的三项校验、顺序执行与 State 共享，强调部分失败隔离。
6. 最后给离线指标和边界：默认确定性、embedding/Qwen 关闭、不是开放 Planner。

## 8. 一定不能说错的边界

- 不能说多意图仍检查固定组合白名单；当前已经取消。
- 不能说 embedding 或 Qwen Router 默认在线启用。
- 不能说这是自由规划、自动循环的开放式 Planner。
- 不能把 challenge set 概括成所有指标 100%；次意图精确匹配为 94.4%。
- 不能把五个子图包装成五个自治 Agent。
- 不能说所有步骤都能并行；当前按用户表达顺序执行。
- 不能说“两个候选都过阈值”就一定是多意图；缺少可靠复合结构时会先澄清。
- 不能说澄清问题由 LLM 自由生成；当前根据前两名候选使用确定性模板。
- 不能把待决任务状态说成长期记忆；它不会注入普通 Prompt，完成、取消或切换明确新请求后会清除。
- 不能说所有会话都能跨重启恢复；普通会话写入 SQLite，临时会话只保存在内存。
- 不能声称已经有线上澄清率或任务完成率；当前证据是自动化回归和本地链路验证。
