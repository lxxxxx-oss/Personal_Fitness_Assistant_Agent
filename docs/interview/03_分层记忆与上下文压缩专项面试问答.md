# 分层记忆与上下文压缩专项面试问答

> 对应简历亮点：以 SQLite 持久化完整会话和长期记忆，使用“结构化摘要 + 最近六轮 + 任务相关长期记忆”的分层上下文，在 token 预算内做增量压缩、记忆治理和失败降级。
>
> 使用原则：不要把“数据库里保存了聊天记录”直接等同于“模型拥有记忆”。面试回答要讲清楚存储、提取、召回、注入和治理五个环节。

## 1. 30 秒可直接回答

> 我把会话存储、短期上下文和长期记忆分开设计。SQLite 保存完整 session 和 message，是可追溯事实源；送给模型的短期上下文只包含较早历史的结构化摘要和最近六轮原文；跨会话的稳定偏好、目标和约束作为长期记忆单独存储，再按当前任务检索后软注入。上下文预算按模型窗口减去生成预留和安全余量计算，先用快速估算触发压缩，再用实际 tokenizer 做硬检查。显式偏好可确认后写入，隐式观察至少跨两个独立会话且置信度达到 0.82 才能自动提升，健康敏感信息仍需确认，密钥类内容直接拒绝保存。失败时优先保住最近对话和用户硬约束，而不是让整条请求因为摘要或语义索引故障而不可用。

## 2. 90 秒项目展开

> 首先要区分“全量记录”和“本轮上下文”。每轮 HTTP、SSE、WebSocket 对话都写入 SQLite，便于恢复、审计和重新压缩，但不会把全量历史原样塞给模型。系统保留最近六轮原文；更早消息达到动态摘要水位后，按用户目标、约束、已确认偏好、未决事项等槽位生成最多约 360 Token 的确定性摘要。该水位默认取本轮 Prompt compact Token 线的 35%，并限制在 900—4000 Token，字符线随之派生；它不是让 LLM 自由改写，因此成本低、结果稳定，但语义概括能力有限。
>
> 长期记忆走另一条链路。显式表达如“我乳糖不耐受”先形成候选记忆；隐式观察要跨至少两个独立会话、置信度不低于 0.82 才能自动提升。健康敏感内容需要确认，secret 类内容拒绝入库；记忆支持同槽位替换、过期、撤销和审计。召回以任务感知的 FTS5/LIKE 为主，可选 SQLite+FAISS 语义召回为派生索引，失败时回退关键词检索。
>
> 在请求组装阶段，系统按模型上下文窗口 `C` 计算提示预算 `P=C-G-S`，其中生成预留 `G=1024`、安全余量 `S=256`；达到 `0.8P` 左右开始主动压缩，并在真正调用模型前用 tokenizer 再做硬检查。Chat 和 Diet 会组合系统提示、当前问题、结构化摘要、最近六轮、任务相关长期记忆和必要 RAG 证据；Search/MCP 只取需要的子集。这样模型得到的是“足够相关且受预算控制的工作记忆”，而数据库仍保留完整事实。

## 3. 第一次出现的技术点

### 3.1 会话、上下文与记忆

- **是什么**：会话是按 session 组织的消息记录；上下文是本次请求真正送入模型的 token；记忆是从历史中提取、可在未来复用的信息。
- **解决什么问题**：如果三者混为一谈，要么全量历史不断膨胀，要么截断后丢失用户目标，要么把临时说法误当成永久偏好。
- **项目中怎么用**：SQLite 保存完整消息；摘要和最近六轮构成本轮短期上下文；长期记忆表保存经治理的稳定信息，再按任务召回。
- **类似方案**：仅滑动窗口、纯摘要、每次全文检索、向量记忆、知识图谱记忆、框架内置 checkpoint。
- **为什么选择它**：健身助手既要保留近期对话连续性，也要长期记住目标和禁忌；分层后每类数据都有明确生命周期和失败策略。

### 3.2 短期记忆、长期记忆与工作记忆

- **短期记忆**：最近几轮对话及较早历史摘要，服务当前会话连贯性。
- **长期记忆**：跨会话仍稳定的目标、偏好、约束和经过确认的信息。
- **工作记忆**：本次节点执行真正组装出的有限上下文，可包含短期记忆、长期记忆和 RAG 证据。
- **项目取舍**：长期记忆不是所有历史的备份；完整历史已经在 SQLite 中，长期记忆只保存未来决策真正需要的信息。

### 3.3 滑动窗口与结构化摘要

- **是什么**：滑动窗口只保留最近 N 轮原文；结构化摘要把更早对话压缩到固定槽位，如目标、约束、已确认事实和未完成事项。
- **解决什么问题**：窗口能保留措辞和局部指代，但会遗忘早期重要信息；摘要能保留核心事实，但可能丢细节。二者组合互补。
- **项目中怎么用**：最近六轮不参与摘要，旧消息达到阈值后增量整理为不超过约 360 token 的摘要。
- **类似方案**：LLM 自由摘要、Map-Reduce 摘要、分层摘要树、检索全部历史。
- **为什么选择它**：确定性摘要更便宜、可测试、不会因为摘要模型临时不可用阻塞主链路；代价是语义压缩不如 LLM 灵活。

### 3.4 Token、Tokenizer 与上下文窗口

- **是什么**：Token 是模型处理文本的基本单位；Tokenizer 把字符串转换为 token ID；上下文窗口是一次推理中输入与输出 token 的总容量。
- **解决什么问题**：字符数不等于 token 数，中文、英文、代码和标点的比例不同；只按字符估算可能在真正调用时溢出。
- **项目中怎么用**：先用低成本估算决定是否提前压缩，再用实际 tokenizer 进行硬预算校验；为输出和误差保留空间。
- **类似方案**：固定字符截断、只用 tokenizer 精确计算、依赖 API 自动截断。
- **为什么选择它**：两阶段检查兼顾性能和可靠性，避免每个中间步骤都昂贵编码，也避免最后才发现超限。

### 3.5 上下文预算与增量压缩

- **是什么**：预算公式把模型窗口分给提示、生成和安全余量；增量压缩只处理新增的旧历史，而不是每轮从头总结全部消息。
- **项目中怎么用**：`P=C-G-S`，当前 `G=1024`、`S=256`；约到 `0.8P` 提前触发本轮 compact。持久化摘要是另一阶段，但其水位默认由这条 compact Token 线的 35% 派生，并设置 900—4000 Token 上下限。
- **为什么是两类阈值**：持久化阈值控制何时更新会话摘要，模型预算控制某一次请求是否能安全进入模型，二者职责不同。
- **类似方案**：固定轮数截断、按模型 API 报错后重试、分区配额、动态重要性压缩。

### 3.6 FTS5、LIKE 与可选语义召回

- **是什么**：FTS5 是 SQLite 的全文检索扩展；LIKE 是简单子串匹配；语义召回用 embedding 匹配意思相近的记忆。
- **解决什么问题**：长期记忆条目增多后，不能每轮全部注入；需要按当前任务选出相关信息。
- **项目中怎么用**：任务类型与关键词过滤是默认主链路，FTS5 不可用时可回退 LIKE；SQLite+FAISS 语义索引是可选派生能力，默认不作为系统成立的前提。
- **类似方案**：BM25、向量数据库、知识图谱查询、基于标签的过滤。
- **为什么选择它**：当前长期记忆规模小，确定性检索容易解释；语义召回作为增强，不让其故障拖垮主链路。

### 3.7 记忆候选、证据提升与置信度

- **是什么**：候选记忆是尚未确认或证据不足的观察；提升是满足证据规则后成为可召回长期记忆；置信度是工程决策信号，不等同于严格概率。
- **解决什么问题**：用户一次随口说“最近不想吃鸡胸”不应永久变成饮食禁忌。
- **项目中怎么用**：显式事实优先确认；隐式观察需来自至少两个独立会话且置信度达到 0.82 才能自动提升，敏感健康信息仍不能自动确认。
- **类似方案**：LLM 一次判断、人工审核、贝叶斯更新、时间衰减、事件溯源。
- **为什么选择它**：规则直观、便于回归和面试解释；0.82 是当前工程阈值，不是医学或行业标准。

### 3.8 软注入、硬约束与 Prompt Injection

- **是什么**：软注入把记忆作为“可能有帮助的用户背景”，而不是具有系统权限的命令；硬约束是已经确认且必须遵守的安全或用户限制。
- **解决什么问题**：历史消息或记忆中可能包含“忽略系统指令”等恶意文本，若以高权限拼接会造成提示注入。
- **项目中怎么用**：记忆带来源、类型和置信度，放在系统规则之后；secret 不入库，健康敏感内容需确认，模型不得把记忆当成工具授权。
- **类似方案**：完全信任历史、上下文隔离、结构化字段、策略引擎、人工确认。

## 4. 当前完整链路

```text
每轮输入/输出
  -> HTTP / SSE / WebSocket 统一持久化
  -> SQLite session + message 保存完整事实

旧会话消息
  -> 排除最近六轮
  -> 达到动态字符线或估算 Token 水位
  -> 增量抽取目标/约束/偏好/未决事项
  -> 确定性结构化摘要（约 360 token 上限）

用户事实
  -> 显式陈述 / 隐式观察
  -> 类型、安全性、来源、置信度判断
  -> 显式确认，或跨 >=2 会话且 confidence >=0.82
  -> 健康敏感仍待确认；secret 拒绝
  -> 长期记忆：替换 / 过期 / 撤销 / 审计

新请求
  -> 识别当前任务
  -> FTS5/LIKE 召回相关长期记忆
  -> 可选 FAISS 语义增强，失败则回退
  -> 组装系统规则 + 摘要 + 最近六轮 + 相关记忆 + RAG 证据
  -> 预算 P=C-G-S，80% 提前压缩
  -> tokenizer 硬检查与按优先级裁剪
  -> 模型调用
```

## 5. 高频问题与完整回答

### Q1：你的记忆系统和普通聊天记录有什么区别？

**回答：**聊天记录是原始事实，记忆是面向未来任务提取出的稳定信息。项目把完整消息保存在 SQLite，便于恢复和审计；真正注入模型的是最近六轮、较早历史摘要和与当前任务相关的长期记忆。例如“今天训练很累”留在会话历史里，“长期目标是降低体脂”经过确认后才适合成为长期记忆。这样既不丢原始事实，也避免全量注入。

### Q2：为什么只保留最近六轮？依据是什么？

**回答：**六轮是当前原型在连续性、上下文成本和实现复杂度之间的固定基线，不是通用最优值。它通常足以覆盖当前任务的局部指代，较早信息则由摘要承接。更成熟的实现会按任务持续时间、消息长度和指代关系动态调整，而不是只按轮数。项目会通过长会话回归检查早期目标、最新约束和未决任务是否仍能恢复。

### Q3：为什么不直接把所有历史做向量检索？

**回答：**向量相似不等于对话连续性。最近一轮的“这个动作”可能语义不完整，但在局部上下文中非常关键；硬约束也不能因为相似度低被漏掉。因此项目让最近窗口和确认约束确定性进入上下文，只对长期记忆做相关性筛选。全历史向量检索还会带来重复、时间冲突和旧信息覆盖新信息的问题。

### Q4：结构化摘要具体保存什么？

**回答：**保存能影响后续决策的槽位，例如用户目标、已确认偏好与限制、当前计划、关键结论、未完成事项，不复制寒暄和逐句聊天。摘要只是原始消息的派生视图，完整历史仍保留。若新信息与旧槽位冲突，要记录更新时间并让新确认事实替换旧值，而不是把矛盾文本都拼进去。

### Q5：为什么用确定性摘要，不用 LLM 总结？

**回答：**确定性抽取成本低、延迟稳定、容易测试，也不会因为模型不可用让每轮聊天失败。缺点是对隐含语义和复杂关系概括较弱。当前项目为了可运行原型选择它；生产化可用 LLM 生成候选摘要，再用结构化 schema、事实回指和冲突校验约束，但不应让自由文本摘要成为唯一事实源。

### Q6：什么叫增量压缩？

**回答：**不是每次把全部历史重新总结，而是保留现有摘要，只把新滑出最近窗口的消息合并进去。例如第 7 轮到来时，最旧的一轮进入摘要候选，最近六轮仍保留原文。这样计算量随新增历史增长，而不是随会话总长度反复增长，也减少每次总结措辞漂移。

### Q7：`P=C-G-S` 怎么解释？

**回答：**`C` 是模型总上下文窗口，`G` 是为模型输出预留的 1024 token，`S` 是 256 token 安全余量，剩下 `P` 才是提示输入预算。安全余量覆盖 tokenizer 估算误差、模板变化和工具包装。达到 `0.8P` 就提前处理，而不是等到硬上限报错；最终调用前仍用真实 tokenizer 校验。

### Q8：为什么既有字符阈值又有 token 阈值？

**回答：**字符统计便宜，适合数据库层快速判断；Token 更接近模型真实成本，但提前构建阶段仍只能保守估算。持久化摘要水位默认由 Prompt compact Token 线按 35% 派生并限制在 900—4000 Token，字符线按 4 倍同步派生；请求级 Prompt 预算仍以模型窗口推导并由本地 tokenizer 或远程 provider 最终兜底。两类阈值服务不同阶段，并非重复。

### Q9：如果估算器说没超，实际 tokenizer 说超了怎么办？

**回答：**实际 tokenizer 是硬门槛。系统按优先级裁剪：先去重和缩减低相关 RAG/长期记忆，再压缩较早摘要，最后才缩短最近历史；系统安全规则、当前用户问题和已确认健康约束优先保留。如果仍无法满足预算，则明确失败或切换更大上下文模型，而不是静默截掉关键指令。

### Q10：长期记忆是怎么写入的？

**回答：**先生成带类型、值、来源、时间和置信度的候选，不直接无条件落成“真相”。显式表达可以请求确认；隐式观察至少需要两个独立会话证据且置信度达到 0.82。入库后还要支持过期、撤销、审计和同槽位替换。写入治理和读取召回同样重要，否则记忆越多错误越多。

### Q11：为什么一定要跨两个会话？同一会话说两次不算吗？

**回答：**同一会话中的重复可能只是上下文回声或对同一个临时状态的强调，独立会话能提供更强的稳定性证据。两次仍只是当前项目的低成本阈值，不是绝对真理；敏感信息无论出现几次都需要确认，普通偏好也应结合时间衰减和用户纠正。

### Q12：0.82 是怎么来的？是校准概率吗？

**回答：**不是严格校准概率，而是工程规则中的门槛，用来减少低置信观察自动晋升。面试时不能说它是行业标准。真正生产化应在标注样本上画精确率-召回率曲线，根据“错记”的业务代价选阈值，并做分类型校准；健康禁忌的阈值和普通口味偏好不应相同。

### Q13：健康信息为什么要特别处理？

**回答：**过敏、疾病、用药和伤病会直接影响建议安全，错误记忆的成本远高于记错口味。项目把这类信息标成敏感，需要用户确认；输出也不能做诊断和治疗承诺。生产化还需加密、访问控制、数据最小化、保留期限和删除机制。当前本地原型没有把这些说成完整合规体系。

### Q14：如果用户说“忘掉我的目标”怎么办？

**回答：**长期记忆支持撤销和审计。先定位对应用户、槽位和来源，标记失效或删除可服务数据，并确保派生向量索引同步移除或重建；之后不再注入。完整消息日志是否删除要遵循产品策略和用户授权，不能只删向量不删事实源。当前项目重点实现记忆撤销语义，生产合规还需正式删除流程。

### Q15：新旧偏好冲突怎么处理？

**回答：**不能把两个冲突值都当成当前真相。用同槽位键识别冲突，新确认、来源更直接且时间更近的信息替换当前值，旧值保留审计状态但不再注入。例如用户把训练目标从增肌改成减脂，当前目标只保留减脂，同时记录变更时间。敏感冲突应向用户澄清。

### Q16：任务感知召回是什么意思？

**回答：**不是只按文本相似度，而是先根据当前子图筛选记忆类型。Diet 优先取饮食目标、过敏和热量偏好；Motion 优先取伤病限制和动作历史；Search 不需要注入全部生活偏好。这样既省 token，也减少无关或敏感信息扩散。文本相关性只在任务过滤后进一步排序。

### Q17：为什么语义记忆索引默认不是强依赖？

**回答：**当前记忆规模小，类型、标签、FTS5/LIKE 已能覆盖主路径；语义索引需要 embedding 模型、版本一致性和重建逻辑。如果它失败不应让用户无法聊天，所以设计成派生增强并可回退。数据量和同义表达增加后，再用离线样例证明它相对关键词检索的收益。

### Q18：RAG 和长期记忆有什么区别？

**回答：**RAG 知识通常是面向所有用户的外部资料，例如训练原则；长期记忆是某个用户的目标、偏好和约束。二者来源、权限、更新频率和风险不同。本轮上下文可以同时包含它们，但要清楚标注：知识证据不能篡改用户偏好，用户记忆也不能充当医学事实。

### Q19：SSE 或 WebSocket 中途断开，会不会丢消息？

**回答：**项目统一考虑 HTTP、SSE、WebSocket 的 turn 持久化，不让流式协议绕过记忆层。理想做法是请求开始记录 turn 状态，完成后原子写入最终输出；中断则标记 incomplete，恢复时避免把半段回答当成已完成事实。当前已有统一持久化主线，生产化还需幂等 request ID、事务边界和断点恢复测试。

### Q20：摘要服务失败怎么办？

**回答：**当前摘要是确定性逻辑，本身依赖较少；任何增强组件失败时，主链路优先回到最近六轮加硬约束，并缩减低优先内容。不能因为“记忆更智能”而让基本聊天不可用。降级结果要带可观测原因，例如 summary_failed 或 semantic_index_unavailable，便于排查。

### Q21：如何防止历史记忆里的 Prompt Injection？

**回答：**首先不把任意历史文本当系统指令；记忆只保存允许的结构化类型，secret 和工具授权类内容拒绝；注入时放在安全规则之后并标明是不可信用户背景；工具仍由 schema、权限和节点逻辑校验。生产化还需要内容扫描、来源信任级别和跨用户隔离测试。

### Q22：怎么评测记忆系统？

**回答：**至少分四类：写入准确率，测试该记的是否记、临时信息是否误记；召回质量，测试正确记忆是否进入对应任务；上下文预算，测试长会话是否稳定不溢出；行为结果，测试新目标替换、撤销、敏感确认和组件降级。还要加入多会话时间线和冲突样例，不能只测单轮问答。

### Q23：这套设计最大的边界是什么？

**回答：**确定性摘要可能漏掉复杂隐含关系；固定六轮和按模型预算派生的全局摘要水位仍不是按用户或会话个性化的最优策略；默认检索仍偏规则化；SQLite 是单机原型，当前未实现生产级加密、多租户隔离和分布式一致性。它的价值是把“完整事实、有限上下文、长期记忆、治理和降级”主链路跑通，而不是声称已经替代成熟记忆平台。

## 6. 面试官连续追问示例

### 追问链 A：从“记忆”追到“错误记忆”

1. 什么信息会记？——稳定且影响未来决策的目标、偏好、约束。
2. 一次提到就记吗？——先成为候选；隐式事实需跨会话证据。
3. 错了怎么办？——同槽位替换、撤销、过期和审计。
4. 敏感信息呢？——必须确认，secret 直接拒绝。
5. 如何量化？——按类型统计写入精确率、误提升率和撤销成功率。

### 追问链 B：从“上下文压缩”追到“信息丢失”

1. 为什么压缩？——模型窗口有限，成本和延迟随 token 增长。
2. 压什么？——较早历史，最近六轮和硬约束优先保留。
3. 怎么防丢？——原始消息不删，摘要是派生视图，可重新生成。
4. 怎么判断超限？——快速估算 + tokenizer 硬检查。
5. 摘要错了呢？——保留来源、允许重建，敏感决策回看原文或要求确认。

### 追问链 C：从“本地 SQLite”追到“生产治理”

1. 为什么 SQLite？——本地可运行、事务简单、便于审计。
2. 多用户安全吗？——当前只是原型边界，生产需租户隔离和访问控制。
3. 如何删除？——事实源和派生索引同步处理。
4. 如何加密？——传输、静态数据、密钥管理分层实现。
5. 如何监控？——写入、召回、压缩、降级、撤销和跨用户泄漏指标。

## 7. 容易露馅的说法与正确口径

| 不要这样说 | 建议这样说 |
|---|---|
| “SQLite 就是记忆。” | “SQLite 保存事实；记忆还包括提取、治理、召回和注入。” |
| “超过六轮就删除。” | “原始消息保留，六轮之外进入摘要和按需召回。” |
| “0.82 是科学概率阈值。” | “它是当前工程门槛，生产应按标注集和风险类型校准。” |
| “系统会自动记住所有偏好。” | “只有允许类型且证据充分的信息才能提升，敏感项需确认。” |
| “压缩不会丢信息。” | “压缩一定有损；通过保留原文、结构槽位和优先级减少风险。” |
| “用了向量数据库做记忆。” | “当前是 SQLite 事实源，可选 FAISS 派生索引，默认可回退。” |
| “已经满足隐私合规。” | “原型实现了最小化和撤销思路，生产仍需正式加密与合规体系。” |

## 8. 白板讲解顺序

1. 左侧画 SQLite 全量 session/message，不会丢原始事实。
2. 中间分短期：结构化摘要 + 最近六轮。
3. 下方画长期记忆：候选 → 证据/确认 → 生效/替换/撤销。
4. 右侧画任务感知召回与软注入。
5. 写预算公式 `P=C-G-S` 和“两阶段 token 检查”。
6. 最后用一条降级箭头回到“最近六轮 + 硬约束”。

## 9. 当前边界与生产化升级

### 当前已经实现

- SQLite 完整会话和消息持久化。
- 确定性结构化摘要、最近六轮窗口和请求级 token 预算。
- 显式/隐式记忆候选、跨会话提升、敏感确认、secret 拒绝。
- 任务感知召回、撤销/过期/替换和可选语义索引降级。

### 当前没有实现

- LLM 语义摘要及逐事实回指验证。
- 生产级加密、多租户隔离、跨节点一致性和合规删除工作流。
- 按任务动态窗口、分区精确 token 配额和大规模线上记忆评测。

### 生产化优先级

1. 建立多会话 Gold Set，量化误记、漏记、冲突和撤销。
2. 为敏感类型增加人工确认、权限与加密边界。
3. 用 schema 约束的 LLM 摘要做候选，并用原文回指校验。
4. 达到并发瓶颈后再迁移服务化存储与向量检索。
