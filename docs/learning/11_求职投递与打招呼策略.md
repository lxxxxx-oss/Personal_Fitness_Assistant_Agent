# 求职投递与打招呼策略

本文是后续分析招聘岗位、撰写 BOSS 直聘打招呼语和复盘投递效果时统一使用的长期口径。它记录的是稳定事实与决策规则，不保存姓名、电话、邮箱等私人信息。

## 1. 求职定位

### 主投方向

- Agent 应用开发、Agent 研发实习。
- AI Native 应用、AI 全栈、LLM 应用开发。
- RAG、知识库与工具调用相关的应用工程岗位。

这些岗位最能同时利用现有 Agent 项目、真实前端实习和工程交付能力。目标不是纯大模型预训练或纯算法研究岗，也不把自己包装成已有企业级 Agent 生产经验的人。

### 岗位适配梯度

| 梯度 | 典型岗位 | 判断依据 |
|---|---|---|
| 优先投递 | Agent 应用、RAG 应用、AI 全栈 | 核心工作能由现有项目和实习提供直接证据，硬性条件也满足 |
| 可以争取 | Agent 平台后端、工业 Agent、偏工程的算法应用 | Agent 主线匹配，但平台化、分布式、特定后端生态或工业系统经验存在缺口 |
| 谨慎投递 | 纯 LLM 训练、重度微调、模型算法研究、资深平台岗位 | 核心职责不是现阶段的主要能力，仅靠论文或项目关键词不能弥补经验差距 |

“高度匹配”不能只看 JD 中是否出现 LangGraph、RAG、MCP 等同名词。每次必须先检查硬性条件，再检查核心职责是否有真实证据。

## 2. 可以稳定使用的优势

### 2.1 可运行的 Agent 项目

独立开发了个人健身 Agent，可用于证明自己不是只会调用聊天 API，而是做过一条完整的 Agent 应用链路：

- 使用 Python、FastAPI、LangGraph 组织路由、状态和多步骤工作流。
- 实现受约束的混合意图拆解、工具调用、内部工具治理和 MCP 主链路。
- 实现 SQLite + FAISS Dense 检索、BM25 召回与 RRF 融合的混合 RAG，并保留来源与降级路径。
- 实现完整会话、近期原文、历史摘要和长期用户事实的分层记忆与上下文压缩。
- 具备接口联调、自动化测试、技术文档和 Docker 原型交付经验。

当前边界：RAGAS 三指标评测入口和 80 条分层黄金集已具备；2026-08-08 父子索引 v2 的 Dense/Hybrid `Recall@5` 都是 `0.967`，MRR 分别为 `0.844` 和 `0.893`，42 条 tuning 与 18 条 holdout 的 RAGAS 分别为 `1.000/0.902/0.786`、`1.000/0.815/0.762`。当前层级聚合 v3 已通过结构与回归测试，正式指标待复评。因此投递时可以说“接入 RAGAS、建立分层黄金集、跑通 tuning/holdout 闭环，并用检索指标诊断融合排序”；不能把 v2 分数写成 v3 结果，也不宜填写最终高分或泛化提升比例。

### 2.2 真实前端实习的可迁移价值

实习方向是前端，不应包装成 Agent 实习；它对 Agent 应用岗的价值在于证明真实业务交付能力：

- 熟悉 TypeScript/JavaScript、React、微信小程序和接口联调。
- 在无人机实时监测与控制模块中处理 MQTT 消息、复杂状态同步、指令调度、执行反馈、视频/GIS 联动与异常隔离。
- 经历过真实需求、多人协作、Git 版本管理、问题排查和功能交付，而不只是个人 Demo。

对于 AI 全栈、Agent 产品落地和需要前端交互的岗位，这段经历是明显加分项；对于纯模型算法岗，它只能证明工程能力，不能代替训练和研究经历。

### 2.3 补充优势与触发条件

| 优势 | 什么时候主动写进打招呼语 | 表达边界 |
|---|---|---|
| 已发表深度学习相关论文 | JD 提到机器学习、深度学习、算法、论文或科研优先 | 只说已发表和相关方向，不虚构论文级别、模型细节或与 LLM 微调的关系 |
| 熟练使用 Git、了解 Linux | 默认完整骨架固定保留 | 体现日常工程基础，不扩展成 Linux 运维或系统开发经验 |
| Claude Code、Codex 等 AI Coding 使用经验 | 默认完整骨架固定保留 | 表达为实际开发辅助经验，不说成自己实现了这些产品 |
| 可长期稳定实习 | 实习岗位的默认完整骨架固定保留 | 写“可长期稳定实习，时间可配合岗位要求”；只有本人确认具体数字后才写几个月、每周几天 |
| TypeScript/React 实习经验 | AI 全栈、前端 Agent、可视化或产品落地岗位 | 强调真实交付与迁移能力，不冲淡 Agent 项目主线 |

## 3. 每个岗位的客观分析顺序

收到岗位截图后，固定按以下顺序判断：

1. **硬性条件**：学历与年级、专业、城市、到岗天数、实习时长是否满足。硬条件不满足时不能判定为高匹配。
2. **核心职责**：岗位主要是在做 Agent 应用、平台后端、RAG、Prompt/评测，还是模型训练。区分主职责与加分项。
3. **直接证据**：现有项目、实习或论文中，哪些经历能证明对应能力。
4. **可迁移能力**：例如前端实习能够证明事件驱动、状态管理和交付，但它不是 Agent 开发经历。
5. **缺口与风险**：明确缺少的技术栈、业务领域和生产经验，判断能否短期补齐。

最终使用三个结论：

- **优先投递**：硬性条件满足，多数核心职责有可解释的直接证据，缺口不是岗位主线。
- **匹配、可以投递**：硬条件满足，核心能力部分匹配，但存在一到两个需要坦诚说明的工程或业务缺口。
- **匹配较弱/不建议主投**：硬条件不满足，或核心工作主要是模型训练、资深平台建设等当前没有证据的方向。

这是一套个人投递决策规则，不是行业统计标准。以后不能因为 JD 出现几个熟悉的技术名就直接说“高度匹配”。

## 4. 打招呼语的统一写法

### 4.1 结构

后续默认使用一套完整骨架：

1. 开头只替换实际应聘的岗位名称。
2. 正文稳定保留 Agent 项目、核心机制、AI Coding、Git/Linux、Docker 和实习稳定性，用于完整呈现用户优势。
3. 只有 JD 明确提到论文、科研、机器学习、深度学习或算法经历时，才追加论文发表经历。
4. 对医疗、金融、工业等明确的垂直行业岗位，将“健身 Agent”改成中性的“Agent 应用项目”，避免让无关业务领域抢占注意力；但不能改写成“医疗 Agent”“金融 Agent”等表述，也不能暗示已有对应行业经验。

这套正文是用户确认的完整优势版本，后续不因每个岗位随意删减。它仍然只选取能被项目和实际经验证明的关键能力，不继续堆叠简历中的全部技术名词；只有用户明确要求短版，或岗位极度垂直时，才使用下方专项短版。

### 4.2 默认完整骨架（后续优先使用）

> 您好，我想应聘【岗位名称】。我独立完成过基于 Python、FastAPI 和 LangGraph 的健身 Agent，实现了混合意图路由、分层记忆与上下文压缩、上下文预算控制、自动化回归及 RAGAS 评测入口；熟练使用 Claude Code、Codex 进行代码分析、开发与测试，熟练使用 Git 进行版本管理，了解 Linux 基本操作并具备 Docker 容器化经验。可长期稳定实习，时间可配合岗位要求，希望进一步沟通。

其中使用“混合意图路由”，不使用含义模糊的“多意图路由导航”；使用“熟练使用 Claude Code、Codex”，不使用语法不完整的“能够熟练 Claude Code、Codex”。“RAGAS 评测入口”准确对应当前已实现边界；若进一步说“已跑通 tuning/holdout”，也要主动说明小样本、本地裁判和未达到生产验收的边界。

垂直行业岗位使用以下中性替换，其他内容保持不变：

> 您好，我想应聘【岗位名称】。我独立完成过基于 Python、FastAPI 和 LangGraph 的 Agent 应用项目，实现了混合意图路由、分层记忆与上下文压缩、上下文预算控制、自动化回归及 RAGAS 评测入口；熟练使用 Claude Code、Codex 进行代码分析、开发与测试，熟练使用 Git 进行版本管理，了解 Linux 基本操作并具备 Docker 容器化经验。可长期稳定实习，时间可配合岗位要求，希望进一步沟通。

### 4.3 AI 全栈或产品落地岗专项短版（备选）

> 您好，我希望应聘贵司 AI 全栈/Agent 开发实习。我有 TypeScript、React 的真实前端实习经历，也独立完成过 Python、FastAPI、LangGraph Agent 项目，覆盖工具调用、RAG、记忆和接口联调，能兼顾 Agent 能力与产品落地。希望有机会进一步沟通。

### 4.4 RAG 或算法应用岗专项短版（备选）

> 您好，我希望应聘贵司 RAG/Agent 实习。我在个人项目中实现了 SQLite + FAISS、BM25 与 RRF 组成的混合检索，并接入 RAGAS 评估上下文相关性、忠实度和答案相关性；同时有深度学习论文发表经历。希望有机会发送简历并沟通。

### 4.5 Agent 工程或平台岗专项短版（备选）

> 您好，我希望应聘贵司 Agent 工程实习。我独立完成过 LangGraph Agent 项目，实践了状态编排、工具调用、MCP、记忆与 RAG，并具备 FastAPI、Git、Linux 基础、测试及 Docker 交付经验。岗位需要的平台化能力也是我希望继续深入的方向，期待进一步沟通。

### 4.6 论文经历的触发式追加

当 JD 明确提到论文、科研、机器学习、深度学习或算法经历时，在工程能力之后、实习时间之前追加：

> 另外，我有深度学习相关论文发表经历。

JD 不涉及这些要求时不主动加入，避免让论文弱化 Agent 工程主线。除论文句外，Git/Linux、AI Coding 和长期实习已经包含在默认完整骨架中，不再重复追加。

## 5. 不得过度包装的内容

- 不把前端实习称为 Agent 实习，也不声称在实习中落地过 Agent。
- 不把单个个人项目说成多个企业级 Agent 项目或线上大规模生产系统。
- 不把五类任务工作流说成开放式多智能体自治平台。
- 不声称做过 LLM 训练、微调、LLMOps、线上 A/B 测试或已有线上业务指标，除非以后真正补齐证据。
- 不把 RAGAS tuning 调参分数写成 holdout 或生产高分，也不编造混合检索提升百分比。
- 不把“了解”写成“深入掌握”，不把后续规划写成当前已实现。
- 不因岗位写了 Node.js、Bun、Effect、MES、CAD、CAE 或分布式系统，就把相邻经验包装成直接经验。

可信的包装方式是强调：完整链路、选型理由、故障降级、评测意识、真实交付和清晰演进路径。面试中能够从价值讲到代码证据，再主动说出边界，比堆更多名词更有说服力。

## 6. 用投递漏斗验证简历

只看“投了多少次”容易误判，建议记录以下漏斗：

```text
有效投递/打招呼 -> 有意义回复 -> 成功发送简历 -> 面试邀约 -> 后续面试
```

主要观察“面试邀约数 ÷ 成功发送简历数”，因为它更接近简历本身是否通过筛选；“回复数 ÷ 打招呼数”更多反映岗位选择、开场语和活跃度。

可先累计 30—50 个硬性条件满足且方向相符的有效样本再判断。个人复盘时可暂用以下经验线，不把它当行业统一标准：

- 面试邀约率达到约 10%，说明简历基本能通过初筛。
- 达到约 15%—20%，说明当前定位与简历竞争力较好。
- 长期低于约 5%，需要检查岗位定位、简历证据和关键词是否失配。

如果几乎没人回复，先改岗位筛选和打招呼语；如果愿意收简历但没有面试，重点改简历与岗位匹配；如果面试不少但无法推进，重点补项目讲解和技术基础。

现阶段不必为了“项目数量”仓促增加另一个浅层聊天机器人。一个可运行、可评测、能深入防守的 Agent 项目，配合真实实习和论文，足以支撑 Agent 应用实习的初筛。若以后补第二项目，应优先选择互补的 MCP/Tool Hub、Agent 评测平台或真实业务自动化，而不是重复做一个 RAG 聊天 Demo。

## 7. 后续岗位截图的固定输出

以后每收到一个岗位，按以下格式给出：

1. 结论：优先投递、匹配可投，或匹配较弱。
2. 硬性条件：逐项确认，未知项明确标记为待确认。
3. 真实匹配点：只列能被项目、实习或论文证明的能力。
4. 缺口与风险：说明是否影响主职责，以及面试时如何诚实回答。
5. 定制打招呼语：默认只替换岗位名称并保留完整优势正文；垂直行业岗位将“健身 Agent”中性化为“Agent 应用项目”，论文按触发条件追加。只有用户要求短版或岗位极度垂直时才切换专项短版。
