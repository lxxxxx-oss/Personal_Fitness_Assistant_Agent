# 高频技术问答

这篇文档用于准备面试官最可能追问的问题。每个问题都分成三部分：

- **先这样回答**：面试现场先说结论。
- **你需要理解**：帮助你真正理解答案。
- **继续追问**：准备下一轮深入问题。

不要逐字背诵。先记住结论和逻辑，再换成自己的语言。

## 一、项目与智能体架构

### 问题 1：为什么这个项目算智能体，不是普通聊天机器人？

**先这样回答**

> 因为系统不会把所有问题直接交给大模型生成答案。它会先判断任务类型，再选择知识检索、联网搜索、动作算法或外部工具，并把执行结果、来源和错误写回状态，最后生成回答。大模型只是系统中的语言能力，不是唯一执行者。

**你需要理解**

普通聊天通常是“一次输入、一次生成”。智能体至少增加了任务选择、状态、工具和执行流程。本项目的证据包括 Router、LangGraph 子工作流、ToolRegistry、Memory 和执行轨迹。

**继续追问**

如果面试官问“用了工具就一定算智能体吗”，回答：工具调用本身不够，关键还在于系统是否能够根据任务选择工具、管理状态、处理失败并形成可验证的执行闭环。

### 问题 2：为什么使用 LangGraph，不直接写条件判断？

**先这样回答**

> 条件判断适合少量固定分支，但项目还有共享状态、多个子工作流、组合任务、错误隔离和结果合成。LangGraph 用节点、边和状态明确表示这些关系，使流程更容易解释、测试和扩展。

**你需要理解**

LangGraph 不是为了让代码显得复杂，而是让“当前执行到哪里、状态里有什么、下一步去哪里”变得明确。它特别适合需要受控流程的智能体。

**继续追问**

如果只有两个简单分支，手写条件判断更合适。选择 LangGraph 的理由必须来自流程复杂度，而不是框架流行度。

### 问题 3：系统的总体架构是什么？

**先这样回答**

> 我把系统分为接入层、控制层、能力层和保障层。FastAPI 负责接收请求；Router 和 LangGraph 在 `chat`、`search`、`motion`、`diet`、`mcp` 五个代码分支之间选择并编排；RAG、搜索、动作算法和 MCP 完成具体任务；Memory、工具结果、降级和评测负责上下文与稳定性。Knowledge/RAG 不是顶层分支，而是 Chat 与 Diet 会调用的内部能力。

**你需要理解**

四层之间是职责关系，不是四个独立程序。分层的价值是面试官追问某个问题时，你能迅速指出它属于哪一层。

**继续追问**

如果问“ToolRegistry 属于哪一层”，可以说它位于能力与保障的交界处：登记具体工具，同时治理参数、权限、失败和审计。

## 二、路由与多意图

### 问题 4：Router 是不是只靠关键词？

**先这样回答**

> 不是。Router 以加权规则为稳定基础，同时使用组合模式、置信度歧义降级和主/次能力识别；embedding 样例匹配和本地 Qwen 只在无规则形成决定时作为可选路径。Qwen 完成过对比验证，但没有带来准确率净收益且延迟更高，因此默认关闭；embedding 也要等更大评测集证明净收益后再启用。

**你需要理解**

完全关键词容易误判同义表达，完全大模型路由又可能慢且不稳定。项目使用混合方案，把常见明确任务留给确定性策略，把困难样本单独评测。

**继续追问**

如果问“模型更智能，为什么不用”，回答：技术选择要看评测收益。模型如果没有改善困难样本，却增加延迟和不确定性，就不应该为了技术名词强行启用。

### 问题 5：一句话包含两个任务时怎么办？

**先这样回答**

> Router 会记录主意图和次意图，并根据用户原句生成有序路由计划。可靠多意图不再检查固定组合白名单，只校验意图是否合法、是否重复和是否超过三步；执行时逐个进入子图，某一步失败会保留其他成功结果，最后统一合成。

**你需要理解**

多意图不等于完全开放 Planner。当前只是从五个已注册意图中形成最多三步的顺序计划，不会动态发明任务、循环、并行或跨步骤依赖；这种受控编排更容易测试每一步成功与否，也适合面试演示稳定性。

**继续追问**

如果未来升级为真正的开放式规划，还需要补步骤依赖、总预算、循环上限、并行调度和任务成功判定；当前的部分失败保留策略已经落地。

## 三、知识检索与联网搜索

### 问题 6：RAG 的完整流程是什么？

**先这样回答**

> 离线阶段先按标题、段落和句子形成父块，再切成更小的检索子块，用 bge-small-zh-v1.5 把章节路径和子块正文向量化，将父子关系、来源、章节和向量持久化到 SQLite，并据此构建 FAISS 索引；在线阶段由 Dense 与 BM25 各召回子块，经 RRF 融合后回填父级正文、折叠同父命中，将最多 Top-5 证据注入 Prompt，再让所选 Qwen 或 DeepSeek 模型基于证据回答。

**你需要理解**

RAG 不是一个单独工具，而是一条从数据准备、检索到回答生成的链路。任何环节都可能影响效果。

**继续追问**

当前知识库是 12 份结构化文档的原型规模，而且 Markdown 结构清晰，因此采用确定性父子分块而不是 LLM 语义切块：小子块提高定位精度，回填父块保留上下文，同时仍便宜、可复现。旧单层方案有 81 个 chunk；2026-08-08 父子版重建后有 87 个父级检索单元。常见追问还包括 Top-K 怎么选、没有相关资料时怎么办、如何防止模型忽略证据。

### 问题 7：SQLite 和 FAISS 在项目里怎样分工？

**先这样回答**

> SQLite 负责持久化 chunk、来源、章节、模型信息和 float32 向量，FAISS 负责进程内相似度搜索。项目对向量归一化后使用 `IndexFlatIP` 做精确余弦排序，并在启动时从 SQLite 重建索引，因此不必重新计算 embedding。

**你需要理解**

SQLite 和 FAISS 都不负责生成回答，也不自动保证检索质量。前者解决可恢复、可追溯的持久化，后者解决本地向量搜索效率。

**继续追问**

如果问“为什么不用 Milvus”，可以回答：当前只有 12 份文档，且是单机面试原型，SQLite + FAISS 已能满足持久化、精确检索和重启恢复，同时显著降低部署成本。若生产数据量、多实例共享或元数据过滤需求增长，可以保持 Retriever 接口不变迁移到 Milvus、Qdrant 或 pgvector。

### 问题 8：RAG 怎样评测？

**先这样回答**

> 我更关注 RAG 最终能否生成可靠答案，所以主评测使用 `eval_rag.py` 让可回答样例走真实检索与生成链路，再由 RAGAS 分别检查上下文相关性、回答忠实度和答案相关性。`eval_retrieval.py` 中的 Recall@K、MRR 只用于开发阶段定位召回或排序问题，不与 RAGAS 合成总分。黄金集有 80 条：60 条可回答进入主评测，20 条无答案单独观察；同时拆成 tuning 与 holdout，降低边调参边验收造成的数据泄漏。2026-08-08 当前父子版检索的 Dense/Hybrid `Recall@5=0.967/0.967`、`MRR=0.844/0.893`；42 条 tuning 和 18 条 holdout 的 RAGAS 分别为 `1.000/0.902/0.786`、`1.000/0.815/0.762`。这说明融合排序有效，但父子分块相对旧单层基线没有显著提分；holdout 更低，因此不能把 tuning 分数包装成最终泛化高分。

**你需要理解**

“接入 FAISS”只能证明链路存在，不能证明效果好。评测必须从真实问题、期望证据和回答标准出发。

**继续追问**

如果问当前证据，说明项目已完成 SQLite 持久化、FAISS 重启重建、同源替换、模型/维度冲突保护、内存降级，以及父子分块的代码契约测试，并准备了 80 条带参考答案和分层元数据的黄金集。2026-08-08 当前父子版对 60 条可回答样例复测：Dense 与 Hybrid 都命中 `58/60`，`Recall@5=0.967`；MRR 分别为 `0.844/0.893`，说明 Hybrid 没有多找回 Top-5 正确证据，但第一个正确证据的平均排名更靠前。RAGAS 侧的 tuning/holdout 三项均分分别为 `1.000/0.902/0.786` 与 `1.000/0.815/0.762`。`1.000` 是对拼接后的 Top-5 整体做离散判断，不代表每个 chunk 都完美；合理结论是“当前链路已完成可复现回归，融合排序有效，但父子分块未呈现显著提分，生成泛化仍有波动”，不是“当前版本已经生产级高分验收”。

如果追问模型角色，回答：`BAAI/bge-small-zh-v1.5` 是运行时检索 embedding；用户选择的本地 `Qwen3-0.6B` 或 DeepSeek API 模型是运行时回答模型；`Qwen3-8B` 只在历史离线评测中充当 RAGAS 裁判。三个模型角色不要混用。

**追问：Recall@5 和 MRR 是怎么计算的？这个结果算好吗？**

> `Recall@5` 看 Top-5 里有没有命中正确证据：本项目要求来源文件匹配，并且片段内容包含黄金集标注的关键证据。当前父子版的 60 条可回答样例中，Dense 与 Hybrid 都命中 58 条，所以都是 `58/60=0.967`。`MRR` 看第一个正确证据排第几名：排第 1 得 1 分，排第 2 得 0.5 分，排第 3 得 0.333 分，没找到得 0 分，再对全部可回答样例取平均；当前 Dense 为 `0.844`，Hybrid 为 `0.893`。这说明当前 Top-5 覆盖较稳、融合排序有收益；但相对旧单层基线变化很小，而且知识库与留出集规模不足以支持生产级结论。

**追问：既然线上用混合检索，为什么还要分 Dense 和 Hybrid 计算？**

> 这是消融对比，不是两套运行时方案。运行时默认走 Hybrid，但单独保留 Dense 指标，可以证明 BM25 + RRF 到底增加了什么，也能发现副作用。当前父子版数据正好说明这一点：两者 Recall@5 持平，而 Hybrid 的 MRR 更高，说明 BM25 + RRF 没有扩大 Top-5 覆盖，却把已有正确证据排得更靠前。与旧单层结果对比后变化很小，因此只能确认结构升级没有明显回退，不能宣称显著提升。

**追问：Hybrid 的 MRR 怎么提升？**

> 优先不加重模型，而是调排序：第一，网格搜索 `candidate_k` 和 `rrf_k`，例如 `candidate_k=10/15/20/30`、`rrf_k=20/30/40/60`；第二，做加权 RRF，让 Dense 在语义问法中权重略高，BM25 在数字、单位、动作名场景权重略高；第三，对同时被 Dense 和 BM25 命中的片段、包含关键数字单位的片段、权威来源片段加轻量 boost；第四，回看分块，避免正确内容被过长或过碎的 chunk 稀释。Cross-Encoder reranker 可以作为生产化方向，但不是当前面试原型的第一优先级。

**追问：BM25 和 RRF 分别是什么？**

> BM25 是经典关键词检索算法，核心看词项出现次数、词项稀有程度和文档长度归一化。它很适合动作名、缩写、数字、单位和机构名，比如 `150-300 分钟`、`1.6g/kg`、`WHO`，但对同义改写不如 Dense。RRF 是 Reciprocal Rank Fusion，用来融合多路排序结果，它不比较 Dense 和 BM25 的原始分数，而是按名次给分，类似 `1 / (k + rank)`，再把多路分数相加，所以实现简单、稳定，也不需要分数校准。

**追问：RRF 和 MRR 都有 reciprocal rank，区别是什么？**

> RRF 是线上检索时的排序融合方法，用来决定最终把哪些上下文排在前面；MRR 是离线评测指标，用来评价正确证据是否排得靠前。最短记忆法：RRF 负责“怎么排”，MRR 负责“排得好不好”。

### 问题 9：RAG 和 Tavily 搜索有什么区别？

**先这样回答**

> RAG 负责本地、稳定、可控的领域知识；Tavily 负责最新研究和外部信息。搜索链路还会改写查询、整理标题摘要网址，并基于来源合成回答。

**你需要理解**

区别主要在数据来源和时效性，不在于两者是否都叫“检索”。

**继续追问**

如果问来源是否完全可靠，回答：当前实现了来源透传和证据约束，生产化还需要来源可信度分级、逐句引用验证和缓存。

## 四、动作分析

### 问题 10：动作分析为什么不能直接交给大模型？

**先这样回答**

> 动作标准性包含关键点坐标、时间轨迹和相似度计算。大模型适合理解和解释，但精确计算应该交给姿态模型和数值算法。因此项目用 MediaPipe 提取姿态、PoseSequence 统一数据、FastDTW 对齐时间，再由大模型解释结果。

**你需要理解**

这是项目中“大模型与确定性算法分工”最直观的例子。

**继续追问**

如果问 3D 是否绝对准确，说明当前是姿态模型估计的三维关键点，会受到视角、遮挡和模型精度影响。

### 问题 11：FastDTW、余弦相似度和逐关节距离分别解决什么？

**先这样回答**

> FastDTW 解决两段动作速度和帧数不同的问题；余弦相似度衡量整体姿态特征方向；时间对齐后的逐关节平均距离衡量人体结构偏差。多指标结合比单一分数更容易解释。

**你需要理解**

时间对齐是比较动作序列的前提。两个人做同一动作，一个快一个慢，不能按原始帧位置直接比较。

**继续追问**

这些指标仍不能自动指出某个关节的专业错误。进一步纠错需要动作类型、关键关节、周期阶段、标准范围和教练标注。

### 问题 12：视频能上传，是否意味着动作纠错已经准确？

**先这样回答**

> 不完全等同。当前已经打通视频到姿态序列、标准样本比较和结构化反馈，可以说明与参考动作有多接近；专业级纠错还需要更大的标准动作库、动作周期切分、关键点平滑、关节级规则和真实教练评测。

**你需要理解**

这是一种有层次的回答：先说明已完成的价值，再说明准确性的条件，而不是先自我否定。

## 五、工具系统与 MCP

### 问题 13：工具系统是不是只写了几个函数？

**先这样回答**

> 函数只是执行器。工具系统还需要说明工具职责、输入结构、权限、结果、错误、重试、降级和审计。项目使用 ToolSpec 和 ToolRegistry 集中描述这些信息，并用 ToolResult 与 ErrorCode 统一返回。

**你需要理解**

工具治理关注“怎样安全稳定地执行”，不仅是“能否调用”。

**继续追问**

当前 Search、Knowledge/RAG 和 MCP 执行路径已接入 Registry；Motion 媒体链路因为文件和数组边界更复杂，没有强行全面迁移。

### 问题 14：LangGraph、ToolRegistry 和 MCP 有什么区别？

**先这样回答**

> LangGraph 管业务流程，决定先后步骤；ToolRegistry 管具体工具执行，负责参数、权限、失败和审计；MCP 是连接外部工具的一种协议。MCP Client 可以作为一个工具被 Registry 管理，但三者不能互相替代。

**你需要理解**

最简单的类比：LangGraph 是流程图，ToolRegistry 是工具台账，MCP 是外部插头标准。

### 问题 15：自己实现的 MCP Client 做了什么？

**先这样回答**

> Client 通过子进程启动本地 Server，使用标准输入输出发送 JSON-RPC，覆盖 initialize、tools/list、tools/call 和文本结果解析，并将失败转换成统一工具结果。默认 mock 用于保证演示稳定。

**你需要理解**

项目验证的是协议主链路，不是完整生产级 MCP 平台。

**继续追问**

当前还需要增强响应编号匹配、inputSchema 深层校验、并发请求、进程生命周期、超时隔离和真实 Server 兼容性。

### 问题 16：让大模型调用工具安全吗？

**先这样回答**

> 不能默认安全。工具必须来自允许列表，参数必须校验，权限要由系统而不是模型决定，执行还需要硬超时、资源隔离和持久化审计。项目已实现 schema、粗粒度权限标签和进程内审计框架；它能约束原型链路，但不等同于登录鉴权、租户隔离或生产沙箱。

## 六、记忆、服务与质量

### 问题 17：短期记忆和长期记忆有什么区别？

**先这样回答**

> 短期记忆保存当前对话需要的最近消息，长期记忆保存跨会话仍有价值的目标、偏好和约束。PromptBuilder 再根据当前任务和预算选择哪些信息进入本轮上下文。

**你需要理解**

记忆系统不是“保存得越多越好”。重点是写什么、何时召回、如何确认敏感信息、怎样删除和控制长度。

**继续追问**

项目以 SQLite 作为长期记忆事实来源，本地 FAISS 只是可选语义增强；伤病、过敏等敏感信息先进入候选确认。

### 问题 18：为什么不能把所有历史都放进 Prompt？

**先这样回答**

> 历史越长，成本和长度越高，噪声也越多，重要信息反而可能被淹没。项目使用近期窗口、长期记忆检索和 compact 分层管理，再按 Prompt 预算注入。

### 问题 19：HTTP、SSE 和 WebSocket 怎么选择？

**先这样回答**

> 普通 HTTP 适合一次返回完整结果；SSE 适合服务器持续向浏览器推送文本；WebSocket 适合需要双向长连接的客户端。项目同时支持三种方式，共享同一智能体主链路。

**继续追问**

同步 LangGraph 和模型生成通过线程桥接到异步队列，避免阻塞事件循环；本地模型仍由生成锁控制同进程并发。

### 问题 20：自动化测试数字能证明什么？

**先这样回答**

> 它能证明接口、状态流、工具契约、错误处理和算法没有回归，但不能直接证明真实模型回答质量。Router、RAG、Memory 和 Motion 还需要各自的效果评测。

**你需要理解**

测试回答“系统有没有坏”，评测回答“策略效果好不好”，线上数据回答“真实用户场景能不能泛化”。

### 问题 21：项目能直接部署到公网吗？

**先这样回答**

> 当前定位为本地可运行的面试原型，不能直接暴露公网。生产化前要补认证授权、租户隔离、限流、HTTPS、CORS 白名单、隐私治理、依赖就绪检查、模型服务化和多实例存储。

### 问题 22：如何证明项目不是技术名词堆砌？

**先这样回答**

> 每项技术都对应明确问题：LangGraph 管流程，RAG 管稳定知识，Tavily 管最新信息，动作算法管确定性计算，ToolRegistry 管工具执行，MCP 管外部协议，Memory 管跨轮信息，评测管质量。它们由统一状态、错误和执行轨迹连接，不是互相孤立的演示模块。

先说结论

## 八、真实连续追问：从概念到工程设计

### 追问链 1：Agent 到底比固定工作流多了什么

**基础级：什么是 Agent？**

> Agent 是能根据目标和当前状态选择下一步动作，并调用工具获得新信息的系统。大模型只是理解与决策组件；状态、工具、控制流程和反馈共同构成 Agent。

**项目级：你的项目是真 Agent，还是几个接口套了 LangGraph？**

> 判断标准不是框架，而是系统是否形成执行计划、保存中间状态、选择不同能力并合成结果。本项目在 `search`、`motion`、`diet`、`chat`、`mcp` 间路由，允许四种验证过的双任务组合，子工作流将来源、错误和轨迹写回共享状态。因此它是受控工作流型 Agent，不是完全自治的规划 Agent。

**工程级：为什么不开放任意工具循环？**

> 健康场景更重视可预测性。开放循环会带来调用次数失控、成本放大、间接提示注入和高权限误操作。生产化应增加最大步数、总时间和 token 预算，按工具分级授权，高风险写操作人工确认，并记录每一步 trace。只有离线评测证明开放规划确有收益，才逐步扩大自由度。

### 追问链 2：RAG 回答错误怎样归因

**基础级：RAG 为什么仍会幻觉？**

> RAG 只提供资料，不保证检索到正确资料，也不保证模型忠实使用资料。错误可能来自切块、向量表示、召回、过滤、上下文组装或生成。

**项目级：怎样做一次错误分析？**

> 先检查正确片段是否在库中，再看 Dense、BM25 两路候选及 RRF 融合排名；如果已进入最终 Top-K，就继续检查去重和 Prompt 是否保留，最后确认结论能否被证据支持。当前 Hybrid 主链路不设固定相似度阈值，只有纯 Dense 基线和诊断入口仍可使用阈值，因此不能把阈值当作混合检索的必经步骤。

**工程级：怎样证明调整候选数、RRF 参数或最终 Top-K 有效？**

> 先固定知识库、问题集和生成模型，再一次只改一个参数：`candidate_k` 决定 Dense 与 BM25 各自提供多少候选，RRF 的 `k` 决定名次差距在融合分数中的衰减程度，最终 Top-K 决定送进 Prompt 的上下文数量。对比时同时观察 Recall@K、MRR、无关上下文比例、RAGAS 指标和 p95 延迟。扩大候选或 Top-K 可能提高召回，也可能带来噪声和延迟，因此不能只追求单个指标；当前项目采用 `candidate_k=20`、`RRF k=60`、最终 Top-5，完整参数对比实验仍属于待补证据。

**追问：RAGAS 三个指标的底层是怎样算的？**

> 上下文相关性把 query 和检索上下文交给 Qwen 做两次分级判断并取平均，主要评价 Retriever；忠实度先把回答拆成原子事实，再逐条判断能否从上下文推出，近似等于“有依据的事实数除以全部事实数”；答案相关性则根据答案反向生成问题，再用 BGE 计算反向问题和原问题的向量相似度。它们分别解决“找得准、说得真、答得对”，用于定位问题，不合并成一个总准确率。

**追问：忠实度高是否说明答案一定正确？**

> 不一定。忠实度只说明回答能够被检索上下文支持；如果知识库本身写错了，模型忠实照搬也可能得到高分。当前黄金集有人工参考答案，但三个 scorer 没有直接用 `reference` 做答案正确性比对，所以我不会把 RAGAS 三项分数说成标准答案正确率。

**追问：为什么完整评测会比一次聊天慢很多？**

> 因为它是离线质量评测，一条样例不是只调用一次模型。当前调参基线固定的 RAGAS 0.4.3 中，上下文相关性约两次裁判，忠实度包含事实拆分和证据判断，答案相关性默认还会多次反向生成问题，再做 embedding 相似度。42 条可回答 tuning 的生成约耗时 10 分 44 秒、评分约耗时 17 分 48 秒；它不应放进运行时请求链路，冻结参数后再单独跑 18 条 holdout，升级 RAGAS 后还应重新核对 scorer 行为。

### 追问链 3：工具失败如何设计

**基础级：超时、重试、降级分别是什么？**

> 超时限制等待；重试处理短暂故障；降级在主要能力不可用时提供较弱但诚实的结果。三者解决不同问题。

**项目级：当前 ToolRegistry 做到了什么？**

> `ToolSpec` 描述参数、权限、重试错误码、fallback 和超时策略；Registry 做参数与权限检查、有限重试、统一 `ToolResult` 和审计。必须诚实说明：权限只是调用方传入的粗粒度 allowlist，审计只保存在当前进程；`timeout_seconds` 主要是元数据，Registry 没有强制中断执行器；备用工具契约虽已定义，默认注册工具并未配置 `fallback_tool`。Retriever 的内存回退是自身内部降级，不要与 Registry fallback 混为一谈。

**工程级：为什么不能所有失败都重试三次？**

> 参数错误和权限拒绝重试无意义；非幂等写操作可能造成重复副作用；持续故障时同步重试会放大流量。应按错误类型和幂等性决定重试，使用指数退避与随机抖动，并设置整条请求的截止时间；高错误率时用熔断或限流保护依赖。

### 追问链 4：Memory 怎样既有用又安全

**基础级：为什么不保存所有对话？**

> 并非所有内容都有长期价值，全量保存会增加噪声、成本、隐私风险和错误记忆。

**项目级：本项目怎样存和取？**

> SQLite 保存可修改、可删除、带有效期和替代关系的事实；FTS5/LIKE 做基础检索，本地 FAISS 可作语义增强；PromptBuilder 按任务和预算注入近期窗口及相关长期记忆。显式普通内容可直写，伤病、冲突和保守识别出的隐式长期信息先确认。

**工程级：多租户最危险的问题是什么？**

> 是跨用户召回和敏感信息泄露。生产化必须在查询层强制用户或租户过滤，不能只靠 Prompt；还要加密、最小化保存、保留期限、删除传播、审计和越权测试，评测中加入“绝不能召回”的负样本。

### 追问链 5：怎样定义 Agent 成功

**基础级：为什么 HTTP 200 不等于成功？**

> 200 只说明服务完成响应，不说明路由正确、工具有效、回答有依据或用户目标达成。

**项目级：本项目应拆哪些指标？**

> 路由看意图和计划准确率；RAG 看召回与忠实度；工具看成功率、错误码和 fallback；Memory 看写入、召回和误注入；Motion 看关键点质量、对齐和教练标注；整体看任务成功率、延迟和成本。

**工程级：自动评测能直接决定上线吗？**

> 只能作为门槛的一部分。LLM-as-judge 需要固定 rubric、校准样本和人工抽检；离线集也可能不代表线上分布。单元测试、专项评测、红队集、灰度指标和用户反馈应共同形成质量闸门。

## 九、工程词汇必须能落到措施

下面是生产化分析模板，不是当前代码已经全部落地的能力。面试时应先说当前基础，再用这一列回答“如果上线怎样补”。

| 术语 | 普通话解释 | 生产化落地方式（当前未全部实现） |
|---|---|---|
| 幂等 | 同一请求重复执行不产生额外副作用 | 写记忆使用业务唯一键，重试前判断工具是否幂等 |
| 截止时间 | 整条请求最多允许花多少时间 | 给路由、检索、工具和生成分配总预算 |
| 熔断 | 依赖持续失败时暂时停止调用 | 外部搜索或 MCP 高错误率时快速失败并诚实降级 |
| 背压 | 下游处理不过来时限制上游 | 视频分析用有界队列，满载时排队或拒绝 |
| 可观测性 | 用外部证据解释系统内部发生了什么 | 统一 trace_id，记录节点、工具、延迟、错误和降级 |
| SLO | 给用户体验设可衡量目标 | 任务成功率、p95 首 token、错误率和泄露事件 |
| 灰度 | 少量流量先用新版本 | 新 Router、Prompt 或索引先小流量验证并可回滚 |

完整工程回答通常包括“触发条件、采取措施、监控指标和恢复方式”。只说加缓存、加重试、加监控仍然不够。
