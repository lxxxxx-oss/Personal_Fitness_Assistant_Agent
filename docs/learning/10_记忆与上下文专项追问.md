# 记忆与上下文专项追问

这篇文档专门帮助你回答简历中的“分层记忆与持久化会话压缩机制”。目标不是背诵复杂名词，而是能够说明：为什么要分层、当前代码怎样工作、评测发现过什么问题、边界在哪里、生产化会怎样升级。

## 1. 先理解四个概念

### 1.1 完整会话

完整会话是 SQLite 中按 `user_id + conversation_id` 保存的全部用户消息和助手回答。它解决服务重启后如何恢复、怎样审计历史的问题，但不会把全部内容直接交给模型。

替代方案是只保存在进程内存中，实现简单，但服务重启后会丢失，也不适合多实例。

### 1.2 最近对话

最近对话是当前 Prompt 中保留的近期原文。原文细节最完整，但数量必须受限。项目默认由 `MEMORY_MAX_TURNS=6` 控制，也就是最多 6 轮、12 条消息。

### 1.3 会话摘要

会话摘要是同一个 `conversation_id` 内较早消息的有界结构化记录。项目不调用额外大模型，而是把目标、约束和偏好关联到原始证据片段；`last_compacted_message_id` 记录覆盖边界，下一次只处理新增消息。

可选方案包括模型摘要和向量化摘要。模型摘要更自然，但会增加延迟、成本和事实改写风险；向量检索适合从大量历史中找相关片段，但会增加索引与一致性治理。这个原型优先选择可解释、可测试、能回指原文的结构化证据方案。

### 1.4 长期记忆

长期记忆保存跨会话仍然有价值的目标、偏好和约束，例如“不吃香菜”。它与会话摘要不同：摘要描述当前会话进展，长期记忆描述以后仍可能复用的用户事实。正式记忆带有效期、置信度和替代关系；规则识别出的低风险隐式信息先成为 observation，靠跨会话独立证据晋升，敏感或冲突信息仍需确认。

## 2. 当前链路

```text
请求到达
  → 按 user_id + conversation_id 恢复 SQLite 会话
  → 读取当前 active summary
  → 读取摘要边界之后的最近原文
  → 按当前任务检索已生效的长期记忆，并可读取中间置信度的低风险软记忆
  → Chat/Diet 由 PromptBuilder 组合摘要、最近原文、长期记忆、RAG 证据和当前问题
      （软记忆进入独立低信任区块，不能当作确定事实）
  → 如果本轮 Prompt 超过阈值，执行临时 prompt compact
  → 生成回答
  → 以事务保存完整 user/assistant turn
  → 旧消息超过字符或估算 token 阈值时更新 active summary
  → 摘要失败则保留滑动窗口路径，不影响本轮消息落盘
```

## 3. 一分钟回答

> 我没有把所有聊天记录无限塞进 Prompt，而是分成完整会话、最近六轮原文、结构化证据摘要和长期记忆。较早消息按水位线增量整理成可回指原文的 active summary；隐式长期信息先积累来源证据，低风险内容跨会话达标后才自动晋升，不确定线索只做低信任软注入，敏感和冲突信息保留确认门。本轮 Prompt 过长还会临时 compact；摘要和向量增强都可降级，不阻塞聊天主链路。

## 4. 连续追问与参考回答

### 追问 1：为什么不能直接传全部历史？

> 历史越长，Prompt 成本、延迟和噪声越高，旧信息还可能和新目标冲突。完整历史适合持久化和审计，不适合每轮全部注入，所以要把“保存什么”和“本轮给模型看什么”分开。

### 追问 2：滑动窗口、摘要和长期记忆有什么区别？

> 滑动窗口保存最近原文，强调细节；摘要保存当前会话中较早的进展，强调连续性；长期记忆保存跨会话仍有效的稳定事实，强调复用。三者生命周期和写入规则不同，不能混成一个向量库。

### 追问 3：一次请求具体怎么走？

> 请求先通过用户和会话 ID 恢复会话，再读取 active summary、摘要边界后的近期消息和相关长期记忆。Chat 与 Diet 的核心回答由 PromptBuilder 按预算组装这些内容与 RAG 证据；Search 合成、MCP 格式化等分支只使用任务所需的上下文子集。回答完成后，用户消息和助手回答在同一事务中写入 SQLite，再以 best-effort 方式检查是否需要更新摘要。

### 追问 4：为什么先保存完整 turn，再更新摘要？

> 完整消息是事实来源，摘要只是派生结果。先保证 user/assistant 两条消息原子落盘，即使摘要失败也不会丢失真实历史；下一轮仍可用滑动窗口继续服务。

### 追问 5：怎样避免每次重复总结全部历史？

> `last_compacted_message_id` 是压缩水位线。每次只读取水位线之后的消息，把旧 active summary 和新增候选组合成新摘要，然后原子地将旧摘要标记为 superseded、写入新 active summary 并推进水位线。

### 追问 6：为什么保留 superseded 摘要，不直接删除？

> 原型中保留旧版本有利于审计和排错，可以知道摘要怎样演进。生产环境还需要结合保留期限、隐私删除和存储成本决定是否定期物理清理。

### 追问 7：为什么不用大模型做摘要？

> 当前目标是面试演示和稳定原型。确定性结构化整理没有额外推理延迟，结果可复现，信号还能回指原文证据，不会把用户事实悄悄改写。代价是语义归纳弱、规则覆盖有限；如果生产化，会先建立摘要忠实度数据集，再灰度引入模型摘要，而不是直接替换。

### 追问 8：字符预算和 token 预算怎样配合？

> 我先从当前本地模型配置读取声明的上下文上限 `C`，扣除最大生成预留 `G` 和安全余量 `S`，得到最大输入预算 `P=C-G-S`，再在 `P` 的 80% 设置主动 compact 线 `T`。PromptBuilder 同时检查字符保护线和保守估算 token，任一越线就提前裁剪；真正调用本地模型前，LLMLoader 套用 chat template 并用当前 tokenizer 精确计算输入，既不能超过应用输入预算，也要满足 `input_tokens + max_new_tokens <= C`。跨请求 active summary 是另一条链路，但其触发水位也不再固定：Token 阈值为 `clamp(floor(T×35%), 900, 4000)`，字符阈值默认是它的 4 倍，任一越线就增量整理旧对话。模型文件不可读时会明确标记为 fallback，不能把回退数说成真实上限。

### 追问 9：用户修改目标时怎么办？

> 要区分会话摘要和长期记忆。摘要层会保留旧目标与较新的原文证据，让冲突对回答阶段可见，但不会凭规则自行解释复杂语义；长期记忆对已定义槽位检测到冲突后停止自动晋升，等待确认。确认新值后将旧值标为 `superseded`，并记录 `superseded_by`。这能处理训练目标、饮食偏好等明确槽位，但不等于解决任意语义冲突。

### 追问 10：摘要会不会和最近对话重复？

> 摘要水位线之前的消息进入摘要，水位线之后的消息作为最近原文，两部分按边界去重。扩展评测时曾发现一个真实问题：内存配置保留 6 轮，但 PromptBuilder 只取 6 条消息，相当于只注入 3 轮，导致摘要未触发时出现信息断层。现在 PromptBuilder 已改为跟随 `MEMORY_MAX_TURNS`，并加入回归测试。

### 追问 11：怎样保证不同会话和不同用户不串数据？

> SQLite 查询同时带 `user_id` 和 `conversation_id`，active summary 也按这两个字段读取。评测加入了同一用户两个 conversation 的隔离标记，验证另一个会话的乳糖不耐受信息不会进入当前卧推会话。生产级安全还需要真实认证身份，不能信任客户端随意传入的 `user_id`。

### 追问 12：摘要失败会怎样？

> 加载失败时继续使用最近窗口；更新失败时完整 turn 已经落盘，只是不推进摘要边界。执行轨迹会记录 fallback，但不返回摘要正文和原始异常。这样摘要是增强能力，不是聊天主链路的单点故障。

### 追问 13：14/14 能证明什么？

> 原有 14 条联动样例能证明记忆召回、敏感候选、Prompt 注入、结构化 compact、RAG 来源和多轮摘要链路没有回归；新增 V2 专项测试还覆盖了证据幂等、跨会话晋升、敏感信息不软注入、秘密零落库、过期、撤销和临时对话零持久化。它们不能证明真实用户回答一定更好，也不能代表任意语义抽取、大规模并发或长期运行稳定性。

### 追问 14：active summary 和 prompt compact 是一回事吗？

> 不是。active summary 是跨请求持久化的会话摘要，写在 SQLite `summaries` 表里，用 `last_compacted_message_id` 记录覆盖到哪条消息；它解决“下次请求还能记得较早对话”的问题。prompt compact 是本轮 PromptBuilder 的临时长度保护：先固定保留系统规则、当前问题和已确认的伤病、过敏、禁忌等安全记忆，再把 RAG、已确认长期记忆、结构化摘要、近期对话和会话摘要放入各自已排序的候选队列，按优先级逐轮各尝试一条。某条放不下时会整条跳过并继续其他队列，一轮没有任何新增才停止，最后再用剩余空间装普通信息和软记忆。它只改变本轮注入内容，不替代完整历史，也不写成长期记忆。

### 追问 15：为什么不用 Redis 或 PostgreSQL？

> SQLite 对单机原型足够，事务和查询能力比纯内存可靠，也便于演示。Redis 更适合共享热会话和 TTL，PostgreSQL 更适合多实例事务、权限和并发。生产化可以把接口保持不变，将事实存储迁移到 PostgreSQL，并用 Redis 做短期缓存。

### 追问 16：生产化最先升级什么？

> 第一优先级是认证授权、隐私删除和数据保留策略；第二是在现有轮询装箱、模型硬上限和最终 tokenizer 校验之上，为候选条目补充更可靠的语义安全标签，并用冲突、遗漏和预算利用率评测校准队列优先级；第三才是 PostgreSQL、Redis 和多实例并发控制；有了摘要忠实度基线后，再考虑模型摘要。顺序依据是先保证数据安全和可测，再增加复杂组件。

## 5. 六个多轮摘要场景怎样讲

| 场景 | 验证内容 | 不能证明什么 |
|---|---|---|
| 早期膝伤 | 较早安全约束进入摘要且不重复出现在最近原文 | 最终建议一定医学正确 |
| 多个饮食约束 | 过敏、口味和热量目标可以同时保留 | 自动识别所有隐含偏好 |
| 目标修改 | 摘要层让新旧证据可见；长期记忆的已定义槽位可确认替代 | 不能证明任意自然语言冲突都能自动消解 |
| 两次增量压缩 | 旧摘要复用、水位线推进、最近六轮保留 | 多实例并发下无竞态 |
| 未达到阈值 | 字符和估算 token 均未达到阈值时不生成空洞摘要 | 提前估算与目标模型 tokenizer 完全一致 |
| 会话隔离 | 同一用户不同 conversation 不串数据 | 不能证明已经完成登录鉴权和租户安全 |

## 6. 白板题：画出可降级的会话压缩

先画四块：`ConversationStore`、`Summary Compactor`、`PromptBuilder`、`Long-term Memory`。再补两条边界：

```text
SQLite messages ──按水位线读取──> Summary Compactor
       │                                 │
       │完整历史                          └──> active summary
       │
       └──> recent uncompacted messages ───────┐
                                               ▼
Long-term Memory ──按用户和相关性召回──> PromptBuilder ──> LLM
```

讲解顺序：

1. SQLite messages 是事实来源，summary 是派生数据。
2. 水位线避免重复处理，active/superseded 支持演进审计。
3. Prompt 组合摘要、近期原文、长期记忆和当前问题。
4. 摘要失败走 recent fallback。
5. 单机锁只适合原型，多实例需要版本号或乐观锁。

## 7. 容易说错的话

- 不要说“使用大模型生成高质量语义摘要”，当前是确定性原文摘录。
- 不要说“所有区段都精确分配 token”；当前只有本地模型推理前的总输入边界使用真实 tokenizer。摘要触发水位虽由模型预算动态派生，但候选旧消息的预检查和各区段裁剪仍依赖保守估算；远程 API 最终还要依赖供应商执行硬限制。
- 不要说“解决了记忆冲突”，当前只让新旧信息同时可见。
- 不要说“14/14 证明真实效果很好”，它只是小规模持续回归基线。
- 不要说“支持分布式高并发”，当前是单机 SQLite 原型。
- 不要说“用户隐私已经完整治理”，认证、授权和物理删除仍是生产化工作。
